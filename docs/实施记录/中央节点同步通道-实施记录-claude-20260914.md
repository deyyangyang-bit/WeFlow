## 3. 安全边界（逐条对照任务要求）

| 要求 | 落实方式 |
|---|---|
| 所有 SQL 参数化 | 投影写入只产 `$n` 占位符（`projections.ts`），由 `migration-test` E1/E2 静态断言「不存在手拼 payload 的 SQL」 |
| 令牌只存哈希 | 设备令牌与邀请码均 `secretHash`（sha256）落库，明文只在响应体出现一次；`app-test` B2/B3 断言哈希一致且明文不在任何 store 行里 |
| 日志不输出 token / 邀请码 / AI Key / 敏感信息 | Fastify logger `redact` 排除 `authorization` 与 `idempotency-key`；错误处理只记 `message/stack/code`（不整体落 pg 异常，其 `parameters` 可能带业务值）；`migration-test` E3/E4 静态断言 |
| 配置的日志级别真正生效 | `config.logLevel` 真实传入 Fastify logger（`app.ts` 构造处） |
| 不扫聊天表上行 | `centralProjection.ts` 只读 customer / customer_identity / assignment / account / opportunity / quotation+contract / audit_event / customer_judgment / knowledge_base；无任何聊天或消息表读取 |
| 不传聊天正文 / session_id / WCDB 路径 | `findForbiddenCentralField` 递归拦截 5 类键；judgment 的 session_id 先映射 customer_id，映射不到**跳过该行** |
| 身份值脱敏 | 只上行 `identityHash`（sha256(`type:value`)）+ `identityMasked`（如 `138****11`），原文不出本机 |
| 不可回退的旧路径 / 双写 | 未恢复任何禁用路径；下行只经既有状态机，未新开第二套写入通道 |

## 13. 第六轮：下行指令顶层字段的严格运行时契约（2026-09-15）

> 本轮**不改写既往提交**，以追加提交落地。上一轮的 §12.3 残留中「读不到行则按是否需要补齐决定
> 放行还是拒收」一条**已在本轮作废**，本文档对应处已就地更正。

### 13.1 根因

`shared/centralDownCommand.ts#validateDownCommand()` 的顶层必填**只做 `isBlank()` 判定，形态完全不判**：

```ts
for (const field of spec.required) {
  if (isBlank(payload[field])) return `missing_field:${field}`   // ← 仅此一句
}
```

于是 `assignmentId: 0`、`assignmentId: {}`、`leadId: "41"`、`remindCount: {}` 全部被判为**合法**并返回
`null`。中央 `/sync/commands` 依赖该共享校验器，校验通过即保存指令；本机接收状态机随后对部分值
`Number()` 转换、或根本不使用远端 `assignmentId` —— **畸形指令在业务写入前不被终止**，产生真实的
分配 / 移交 / 回收 / 通知。同一条缺陷也在 `crmDownPayloadCompat.healLegacyDownPayload()`：
transfer 的 `mode` / SLA 已合法时，非正整数或指向不存在行的 `assignmentId` 会被放行。

另一处同源缺陷：顶层 `leadId` 与 `lead.leadId` 的一致性判定写作
`Number(payload.leadId) !== Number(subId)`，`Number("41") === Number(41)` 使「上层字符串、下层数字」
的自相矛盾载荷通过。

## 18. 2026-09-16 宿主原生 Windows Caddy 交付层

### 18.1 背景与判据

## 22. 2026-09-17 销售视图可见性修复：本地署名与中央身份不一致导致「看不到中央分配」

### 22.1 根因（Mac 侧代码定位，未先改代码）

已通过的真实链路：Windows 客户端上行同步、中央落库、解绑、合成 assign 下行（中央 seq 930，
接收端出现合成线索、ACK=applied）。接收端绑定中央销售身份后，销售视图仍看不到该分配，
只有「改成主管（看全部）」或改本地署名才可见——报告先视为待验证现象，据此排查代码链：

```
中央 principal（claimCentralBinding 落 centralSyncEmployeeId/DisplayName/Role 配置，独立于本地身份档案）
  → 下行 assign 落地（applyDownEventTx：assignment.sales_name = payload.salesName = 中央目录显示名）
  → 线索查询/过滤（shared/ownerFilter.isSalesView + filterLeadsForView/buildMyCards/visibleOwnerChips/claimLead）
  → 页面身份（identity:get → 本地身份档案 identityName/identityRole）
```

**根因**：下行 assign 落地的 `assignment.sales_name` 用的是发送侧/中央目录的**显示名**，
而销售视图的归属匹配只用本地身份档案署名（`identityName`）。两者不一致时，
销售视角按「owner = 本人姓名」过滤 → 自己的中央分配一条也看不见；切主管只是绕过
（管理视角看全部，连他人的也看）。

### 22.2 修复口径（不建第二套身份模型、不改 assignment schema、不动历史数据）

- **归属匹配 = 姓名集合（本人署名 ∪ 绑定别名）**：`identityService.getOwnershipAliases()`
  仅在**中央同步已启用且持稳定 employeeId** 时返回 `centralSyncDisplayName` 作为归属别名；
  解绑即清（`disconnectCentralBinding` 已清 centralSync* 配置），不把 displayName 当永久唯一标识；
  历史 assignment 只存姓名（宪法 §1.3），姓名集合匹配是兼容历史行的唯一可行口径；
- **消费点**（同一份 `shared/ownerFilter.isOwnedName / isOwnedLead`，一处定义多处消费）：
  `shared/ownerFilter.filterByOwner`（account/opportunity/contract 展示档）、
  `leadAssignmentView.filterLeadsForView / buildMyCards / canClaimLead / canBindWxid / visibleOwnerChips`、
  `crmAssignmentService.claimLead`（本人判定加别名）、`identity:get` IPC（新增 `nameAliases` 回传，
  前端 5 处经 `identityLikeFromIpc` 统一装载）、`hermesAgent` / `hermesAskDataService`（问数据同口径）；
- **权限边界不动**：视角判定 `isSalesView` 仍只看本地身份档案（中央角色声明不提权）；
  `permission_change` 下行仍只落审计（真权限在服务端）；别名是**设备绑定级**（本设备 =
  该中央员工的设备），换署名不改变设备可见面，展示层过滤非安全边界（宪法 §1.12）；
- **解绑/未绑定/单机/SMB**：别名恒为空、终端投递键仍按本地署名、`getLanSyncConfig` 行为不变。

### 22.2.1 同日复核修订（P1 两项，2026-09-17 第二轮）

复核意见成立，本轮修订：
1. **hub→本地 id 映射命名空间 + 解析顺序**：初版映射只用裸 `leadId`（`centralSync:hubLead:<hubId>`），
   且 `findLocalLead` 先查本地同号 id 再查映射——不同发送设备的本地行号空间互不相通，撞号会
   回收/附着到错误线索。修订为：
   - 映射键带来源设备命名空间 `centralSync:hubLead:<sourceDeviceId>:<hubId>`（`sourceDeviceId`
     取自信封 entityId 的设备前缀；`SyncEventFile` 新增可选 `sourceDeviceId`/`targetEmployeeId`，
     SMB 历史文件不带 → 不写映射、行为不变）；
   - 解析顺序改为「联系方式锚点 → 来源设备映射 → 裸 id 兜底」，且**裸 id 兜底仅用于无 lead
     载荷的指令**（中央 recycle / Phase 1 历史 recycle 异常形态）——带 lead 载荷的 assign/transfer
     在联系方式未命中时即建档，绝不回落裸 id（旧行为会把指令附着到本地同号行，属既有缺陷，
     本轮一并修正，E2 撞号负例钉住：诱饵行不被附着/回收，两台来源设备同名号各自独立）。
2. **归属核对加入稳定 employeeId**：原「姓名集合（署名 ∪ 别名）」中 employeeId 只是别名的
   启用条件，同名员工（显示名一致、employeeId 不同）无法区分——「同名不会混淆」的结论过大，
   本轮收敛。修订为：assignment 新增 `owner_employee_id` 列（幂等 ALTER 加列，不改写任何存量
   归属；宪法 §1.3 补列登记），中央下行 assign/transfer 落地时写入指令声明的 `targetEmployeeId`
   （服务端按它路由到本设备）；归属行带 `owner_employee_id` 时以本机绑定 employeeId 为**权威**
   核对（显示名不参与判定；未绑定一律不可见/不可认领），行未带（历史/本地/SMB）回退姓名集合。
   **同名不串线的结论仅对 owner_employee_id 非空的中央落地行成立**；历史行与本地行仍是姓名口径
   （如实标注：无法追溯区分）。前端 `identity:get` 增加 `employeeId` 回传，5 页经
   `identityLikeFromIpc` 装载；`claimLead` 后端与前端 `canClaimLead` 共用
   `shared/ownerFilter.isOwnedLead` 唯一口径。
