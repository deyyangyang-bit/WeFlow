# P0-2 数据契约盘点

> 2026-08-23 · 纯只读盘点，未改任何 schema / React 页面
> 方法：三路并行精读 + 锚点源码核实，所有结论附 file:line 证据
> 目的：回答「现有数据能否稳定生成一张『AI 当前判断』」
> 结论：能稳定生成约 60%，但有三处硬伤决定它**不可靠 / 不可追溯 / 不可更新**

---

## 0. 定位

P0-2 原以为是「做一张 AI 当前判断卡」。盘点后的结论变了：

> **P0-2 不是先做 UI，而是先修它赖以成立的状态真源。**
> 这是一次**数据可信度工程**，不是一张卡片。

因此 P0-2 拆为三刀（见 §6），本文件是 P0-2A/B/C 的共同设计依据。

## 1. 总览：客户数据横跨三处存储，无统一装配层

| 存储 | 库文件 | 键 | 角色 |
|---|---|---|---|
| `customer_profile` | weflow-sales.db | session_id | 销售侧「当前阶段/活跃」真源（但 6 个写者、中英混存） |
| `account` + `enrich_meta` | weflow-crm.db | id / session_id | CRM 客户档案 + AI 补全 12 字段（带 source/confidence/evidence/locked） |
| insight records / profiles | JSON 文件 | session_id | AI 见解文本 + 关系画像（无 account_id，间接关联） |

AI 结论散落三处：

- `intent_tag_log` —— 阶段判断，部分带证据（P0-1 第一刀）
- `follow_up_task.analysis` —— 五字段 JSON，**仅预热时落库**
- `customerProfile.advice` —— **现场生成、每次打开档案调 LLM、不落库**

## 2. 块1 客户基础画像 —— ✅ 最稳的一块

### 2.1 account AI 补全 12 字段

- 正式列（6）：`company / position / phone / industry / province / city`（crmDbService.ts:203-208）
- custom_fields（6）：`needs / budget / intent_model / purchase_timeframe / competitor / price_sensitive`
- 每字段可追溯：`enrich_meta.fields[field]` = `{source: ai|manual, confidence, at, evidence, locked, model, sourceId}`（crmDbService.ts:212）
- 置信分级：≥0.85 自动写 / [0.7, 0.85) 进 pending 人工裁决 / <0.7 丢弃（crmEnrichService.ts:145-151）
- `sourceId` = 依据的聊天 messageKey（PRD §23 溯源）
- **手动锁定机制**：`setAccountFieldManual` 写 `source='manual', confidence=1, locked=true`（crmDbService.ts:692-707），AI 永不覆盖；人工裁决 accept 写 `source='ai'` 可被更高置信覆盖

### 2.2 缺口

- `account.owner_sales` 无自动化写入路径（仅通用 `crm:entity:update` 可写）→「当前谁在跟进」缺来源

## 3. 块2 当前状态 —— ❌ 最不稳的一块

### 3.1 stage：无单一真源，6 个写者、中英混存、三处口径

`customer_profile.stage` 写者清单（`last-writer-wins`、无锁、无置信度）：

| 写者 | 语言 | 位置 |
|---|---|---|
| 阶段分类器 | 英文 contacted/quoted/negotiating/won/lost | salesStageClassifier.ts:157 |
| AI 见解扫描 | 中文 了解/比价/决策/成交/流失 | insightService.ts:1905 |
| 意向分析 | 中文 | salesIntentService.ts:195 |
| 人工纠正 `sales:intent:correct` | 中文 | main.ts:4801 |
| 通用 upsert `sales:customer:upsert` | 任意字符串 | main.ts:4606 |
| 私聊成交信号 | 英文 won | crmParseService.ts:151 |

三处阶段存储、**零同步**：

| 位置 | 内容 | 唯一写者 | 问题 |
|---|---|---|---|
| `customer_profile.stage` | 混存中英 | 6 个（见上） | last-writer-wins，无归一化写回 |
| `account.sales_stage` | 英文 canonical | `importCustomerFromProfile`（crmDbService.ts:587/593） | 单向投影、只写一次、无条件覆盖可回退；后续阶段变化不回写 |
| `opportunity.stage` | 中文，默认了解 | `opportunityUpsertBySignal` / `opportunityUpdateStage` / `syncOpportunityStageByAccount` | 与 profile 无同步 |

读取侧三套口径并存：`statsOverview` 用 sales_stage（crmDbService.ts:1471）、`getDashboardStats`/`funnelStats` 用 customer_profile.stage（salesDbService.ts:506/692）、档案页兜底 `profile?.stage || account?.sales_stage`（crmIpcHandlers.ts:191）→ **同一客户不同页面可显示不同阶段**。

`last_stage_change_at`（迁移列）：**仅分类器写**（salesStageClassifier.ts:164）；AI 见解/意向/人工纠正/成交信号改写 stage 时都不刷新 →「当前阶段已持续多久」对多数客户不可靠。

### 3.2 intentScore 0-100：阶段映射断链 + 不落库

纯核心 `intentScore.ts` factors：

| # | factor | 规则 | 上限 |
|---|---|---|---|
| 1 | 阶段基础分 | `STAGE_BASE = {了解:30, 比价:60, 决策:80, 成交:100, 流失:5, unknown:0}` | — |
| 2 | 近期意向活跃 | 近 7 天 intent_tag_log 次数 ×6 | 封顶 20 |
| 3 | 久未跟进衰减 | 最后意向/联系时间 ≥14 天起扣，每天 −2 | 封顶 −30 |
| 4 | 商机进展 | 有活跃商机 +10，有数量/金额明细 +5 | ≤15 |
| 5 | 封顶分级 | clamp(0,100)；≥70 高 / ≥40 中 / ≥15 低 | 0-100 |

**断链（明显 bug）**：`STAGE_BASE` 键是**中文**，但 `salesDbService.intentScore`（:737）把 `customer_profile.stage` **原始值**直接传入，未过 `normalizeStage()`。分类器写英文（contacted/quoted…）→ 命中不了中文键 → `?? 0` → **阶段基础分恒 0**，对分类器路径客户系统性偏低。

**不落库**：分数纯 IPC 实时算（crmIpcHandlers.ts:124-136）→ `computeIntentScore`，唯一调用点；`opportunity.intent_score` 列是**死列**（恒 0，全仓无写非零值）。

### 3.3 最近意向变化（intent_tag_log）

- 字段：session_id / stage / confidence / source / reason / message_key / evidence_text / created_at（salesDbService.ts:128-138）
- `source` 取值：auto_message_trigger（分类器）/ ai（AI 见解+意向分析）/ manual（人工）
- **append-only，无去重保证**：仅分类器有"阶段未变跳过"拦截（salesStageClassifier.ts:151），AI 见解/意向/手动每次调用都新增行 → 历史含噪音，**按行统计必然出错**（漏斗已因此显式按"每 session 每档位首次进入"去重，salesDbService.ts:642-668）

### 3.4 阶段依据

- classifier 产出 `stage + confidence + reason(≤20字) + messageKey + evidenceText(≤200字原话)`（salesStageClassifier.ts:21-29）
- 落库：`customer_profile.stage` **只存 stage 值，reason/evidence 一律不写**；`intent_tag_log` 存全量
- **customer_profile 无 reason / stage_changed_at 字段**，只有 `last_stage_change_at`
- AI 见解写 stage 时 reason 是**固定字符串**「见解扫描自动识别」、confidence 恒 0.7（insightService.ts:1906），真实判断依据入库前被 strip（:1897）

## 4. 块3 客户事件/时间线 —— ✅ 结构可用，❌ 缺 4 类关键源

### 4.1 统一时间线 = 9 源

前端装配（CustomerWorkspacePage.tsx:488-498）：`activities`（8 源，crmDbService.accountTimeline :1048-1060 UNION）+ `insights`（insight records JSON）。

| kind | 来源表 |
|---|---|
| crm | activity_log 6 实体：account / contract / logistics / quotation / allocation / payment_record |
| lead | lead_activity |
| opportunity | opportunity_event（created/signal/stage_change/won/lost，最规整的事件表） |
| insight | weflow-insight-records.json（前端第 9 源） |

排序：SQL 升序 → IPC `.reverse().slice(0,40)`（crmIpcHandlers.ts:203）→ 前端合并再倒序 slice(0,40)。**全毫秒一致**，无跨源去重（每 activity_log 行即一事件）。

### 4.2 缺口

- **缺 4 类源**：`intent_tag_log`（阶段判断）、`crm_risk`（风险）、`invoice`（发票）、`contract_status_history`+`quote_signal`
- 风险 `upsertRisk`/`resolveRisk` **不写 activity_log**（crmDbService.ts:868-894）→ 风险不进任何时间线
- 前端时间线**连已有的 intentHistory 都没渲染**（crm:customer:profile 返回了，CustomerWorkspacePage 不用）
- 相邻字段混单位：`customer_profile.last_contact_at` / `account.last_contact_at` 是**秒**（WCDB createTime 回填），时间线本身全毫秒

## 5. 块4 P0-1 证据 —— ⚠️ 三处断点

### 5.1 intent_tag_log 证据写入矩阵

| 写入点 | source | message_key | evidence_text | 位置 |
|---|---|---|---|---|
| 阶段分类器 | auto_message_trigger | ✅ | ✅ | salesStageClassifier.ts:167-175 |
| 意向分析（手动触发） | ai | ✅ | ✅ | salesIntentService.ts:184-192 |
| **AI 见解扫描** | ai | ❌ | ❌ | **insightService.ts:1906** |
| 人工纠错 | manual | ❌ | ❌ | main.ts:4794-4799 |

`extractEvidence` 语义：取最近一条 `role='other'` 非空消息，`evidenceText = text.slice(0,200)`，`messageKey = 该消息 messageKey`（salesStageClassifier.ts:188-198）。只存客户原话、不存 AI reason。

messageKey 格式（chatService.buildMessageKey :3019-3056）：`local:<scope>:<localId>:<createTime>:<sortSeq>:<sender>:<type>` 或 `server:<scope>:<serverId>:...` —— **复合 key，非裸 id**。

### 5.2 三处断点

1. **AI 见解扫描写阶段不带证据**（insightService.ts:1906）—— 与同 `source='ai'` 的 salesIntentService 行为不一致，凡由 AI 见解扫出的阶段判断无证据可查
2. **`source_message_id` 双格式**：承诺提取写裸 `serverId/localId`（salesFollowUpService.ts:329），R3 增量/催办写复合 messageKey（salesActionEngine.ts:579 / insightService.ts:2123）—— 同一列两种 key 无法统一回查
3. **message_key 无反向 resolver**：全仓没有「message_key → 消息原文」函数（唯一解析者是 messagePushService.parseMessageKeySource，用于撤回，与证据回查无关）→ 证据回查只能靠 evidence_text 快照，不能动态回溯

### 5.3 证据时效

- evidence 不失效：append-only 定格（intentCreate 只 INSERT，salesDbService.ts:537-547），无 UPDATE 路径
- `intent_tag_log` 无 TTL、永久累积；读取靠 LIMIT 截断（intentHistory 默认 20，档案 handler 取 10）
- 前端**类型契约未声明证据列**（customerProfileStore.ts:31-39、electron.d.ts:1814），UI 未渲染 → "写了但没展示"

### 5.4 enrich 证据（另一套体系）

`enrich_meta.fields[field]` = `{source, confidence, at, evidence, locked, model, sourceId}`；`sourceId` 语义等同 messageKey（gatherMaterials 取最近消息 messageKey，crmEnrichService.ts:54/64/122/147），但**存不同表的不同字段，与 intent_tag_log.message_key 不共享**。

## 6. 块5 行动上下文 + 商机/风险 —— ✅ 规则层完整，❌ LLM 层不落库

### 6.1 follow_up_task

- 8 类 trigger：rule_r0-r6（action_engine 全量扫描）/ rule_r3_new_no_reply（增量，带 source_message_id）/ rule_r7_quote_followup / rule_r8_logistics_overdue / sla_lead / ai_detected（承诺提取）/ urge_customer（催办）/ manual（前端待办）
- 状态机实际 7 态：pending / done / skipped / superseded / overdue / suspected / followed_ai（**数据层不存在 `ignored`**，仅 UI 注释提及 TodoSidebar.tsx:37）
- 优先级规则化：`PRIORITY_WEIGHT + min(silentDays,30) + STAGE_BONUS`，cap 140；`urgencyTier` ≥100 urgent / ≥60 high
- 主队列截断 DAILY_LIMIT=15

**关键缺口**：
- **规则卡无 due_at**：R0-R8 创建不写 due_at（salesActionEngine.ts:470-478/517-525）→ 永不 overdue，只被重扫 superseded。due_at 真正写值仅 sla_lead / ai_detected / 手动待办
- `customer_profile_id` 列恒 null（schema 有、无调用方写）
- `analysis` 列（迁移列）：五字段 JSON，仅 runFullScan 预热前 8 条时写（salesActionEngine.ts:486-512）；前端点「AI 深度分析」→ 现场算 → **只写前端内存 store 不落库**（todayActionStore.ts:233-259）
- **行动结果零回流**：`chat_opened`/`script_copied` 埋点不存在（全仓 grep 零命中），"打开聊天""复制话术"纯前端动作不落库 → 销售是否真跟进、客户是否回复无回流（**属 P0-4，不混入 P0-2**）

### 6.2 opportunity / crm_risk —— 正则事实数据，非 AI 判断

- **创建者不是 insightService**：`parseBuySignal`/`parseRiskSignal` 是**纯正则规则**（crmParseRules.ts:249-278 / 239-247，仅 isSend=0 客户消息），由 `crmParseService.scanAll` 私聊段调用（crmParseService.ts:143-209）
- `opportunityUpsertBySignal`（crmDbService.ts:791-815）：同 account+同产品+active 累积（quantity/amount 取高，刷新 last_signal_at）；否则新建 `stage='了解', intent_score=0`
- `crm_risk`（crmDbService.ts:80-87）：`upsertRisk` 幂等（同 account+同 risk_type+active → detail \n 追加截 300 字，severity 取高，补齐 opportunity_id）；`resolveRisk` 人工解决。**`source_msg` 是死列**（upsertRisk 不写消息 id）→ 风险无法回查原话
- **AI 结论落点不在 CRM 结构里**：LLM 五字段（whyNow/opportunity/riskSignal/script/nextMove）存 `follow_up_task.analysis`（预热）或 insight records JSON；`generateActionAnalysis` 的 opportunity/riskSignal 文本与 opportunity/crm_risk 表**无关联、不互写**
- 商机/风险只扫私聊，群消息 handle() 不做识别

### 6.3 节流/防重现状

- insight 去重：常量 `INSIGHT_RECORD_DEDUP_MS = 24h`（insightService.ts:51），但注释/日志写「12h」（:1759/1763）——**文案与实现不一致**
- 其它冷却：aiInsightCooldown 120min / SILENCE 24h / ALERT 6h；`follow_up_task.hasRecentTask` 24h + sla 唯一索引；quote_signal.msg_key UNIQUE；CRM processed_msg 消息级幂等
- insight records 存单 JSON 文件整读整写，无并发锁（靠 salesQueue 串行缓解）

## 7. 三个硬伤（本盘点的核心交付）

### 硬伤1 —— Stage 无单一真源

6 个写者、中英混存、三套口径（customer_profile / account.sales_stage / opportunity.stage）零同步、`last_stage_change_at` 覆盖不全、customer_profile 无 reason 字段。

### 硬伤2 —— 证据链存在断点

AI 见解路径不带 messageKey、`source_message_id` 两种格式、无统一 resolver。

### 硬伤3 —— AI 结论没有持久化

summary（现无此字段）/ AI opportunity / AI risk / AI nextMove/script 全部现场生成不落库，无法成为稳定的 Current Judgment。

## 8. 按「AI 当前判断」契约骨架逐字段标注

```text
AI Current Judgment
├── status
│   ├── stage        ⚠️ 能出但不可靠：6 写者混存、三处不同步 —— 需先统一读取真源
│   ├── intentScore  ⚠️ 能算但基础分对分类器路径恒 0（断链）+ 不落库
│   └── trend        ✗ 无现成字段，需从 intent_tag_log 派生
├── summary          ✗ 不存在 —— 现有"AI 下一步建议"现场生成不落库
├── customerFocus[]  ✅ enrich 12 字段带 evidence/sourceId —— 可直接用
├── opportunity      ✅ opportunity 表（正则事实数据）；⚠️ LLM 机会文本不落库
├── risk             ✅ crm_risk 表（正则）；⚠️ source_msg 死列、不进时间线
├── nextAction       ✅ follow_up_task 规则层完整；⚠️ AI nextMove/script 不落库
└── evidence[]
    ├── messageKey   ⚠️ 部分路径带（AI 见解断）+ 无 resolver 回查
    ├── evidenceText ✅ 快照可靠（分类器/意向路径）
    └── at           ✅ 落库时间戳
```

## 9. 结论：能稳定生成什么，不能什么

**现在就能稳定进契约（可解释/可追溯/可更新）**：
- `customerFocus[]`（enrich 字段 + evidence + locked）
- `opportunity` / `risk` 的结构化事实（正则抓的客户原话）
- `nextAction` 的规则层（R0-R8 待办 + due_at/priority）
- `evidence[].evidenceText` 快照（分类器/意向路径）
- 时间线（9 源，缺阶段/风险）基本可用

**"未形成判断"或需先修才能进契约**：
- **stage** —— 当前状态问"现在是什么阶段"得到不稳定答案，是 P0-2 第一块地基
- **intentScore** —— 阶段断链修复 + 决定是否落库
- **summary / AI 机会 / AI 风险 / AI 下一步** —— 现场生成不落库，需改造成"事件 → AI 判断 → 结构化结果 → 持久化 → 证据"
- **证据断点**（AI 见解路径、source_message_id 双格式、无 resolver）—— 决定"可追溯"承诺的真假

## 10. 开发路线调整（2026-08-23 定）

**P0-2 不是先做"AI 当前判断卡"，而是先修它赖以成立的状态真源。** 拆为三刀：

### P0-2A —— Canonical State（先做）
解决：`stage / intentScore / trend`
目标：**同一客户不管从哪个页面看，当前阶段和评分一致。**

- **不做大重构**：不立即收敛 6 个写者，先建 canonical stage 的**读取真源**

```text
CanonicalStage
├── contacted
├── quoted
├── decision
├── won
└── lost
```

- 原则：**AI Current Judgment 只消费 canonical stage**；现有 6 个写者怎么收敛，后面拆
- 优先修明显 bug：`STAGE_BASE` 中文 key vs classifier 英文 stage（§3.2 断链）

### P0-2B —— Evidence Resolver
建立唯一入口 `getEvidenceByKey(messageKey)`：messageKey → WeFlow API → 原消息 → 上下文。
统一 `source_message_id`：**以后全部使用 canonical messageKey，不再接受裸 serverId/localId**。

### P0-2C —— AI Judgment Persistence
`summary / opportunity / risk / nextAction` 改为：消息/事件 → AI 判断 → 结构化结果 → 持久化 → 证据 → Customer Current Judgment。UI 纯读取。
**不再"打开客户档案 → 现场调 LLM"。**

### P0-2 UI
在 P0-2A/B/C 数据契约成立后，最后做 UI（纯最后一层呈现）。

### 边界（本期不做）
- **P0-4 行动结果闭环**（chat_opened/script_copied 埋点）**不混入 P0-2**，避免同时碰 stage/intent/evidence/judgment/telemetry 五线失控
- 不创建 `AI Current Judgment` schema
- 不动 React 页面

```text
P0-1  AI Evidence       ✅ 4338921
P0-2A Canonical State   ← 下一步
P0-2B Evidence Resolver
P0-2C AI Judgment Persistence
P0-2 UI
P0-3  CustomerEvent
P0-4  Action → Outcome
North Star
```
