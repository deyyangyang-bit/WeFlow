### 2.3 `scripts/customer-event-producer-test.ts` — (c) 测试基建（静态断言误伤）

**症状**：14 通过 / 1 失败，A7 失败。

**根因**：A7 的断言是**子串匹配**：

```ts
ok('A7 recordQuoteSignal 内部无事件写（crmDbService 不被事件污染）', !/customerEvent|customer_event/.test(strip(crmDbSrc)))
```

它对**整份 `crmDbService.ts` 源码**做「是否出现过 `customer_event` 字样」的检查。而 `crmDbService.ts:194` 在 `SCHEMA_SQL` 里有一行 **SQL 注释**：

```
-- （ownership_history/outbox_event/audit_event 无删除标记；沿用 intent_tag_log/customer_event
--   先例只带 source/时间列，不设永不更新的 version/updated_by 死列——防 lead 四死列教训）
```

该注释由 `3d442fd`（`feat(crm): Phase 0 数据宪法落地 — D3六表DDL…`，2026-09-03）引入，用途是说明**通用五列约定**，**不是写入**。`strip()` 帮助函数只剥离 `/* */` 与 `//`，剥不掉模板字符串里的 SQL `--` 注释，于是误伤。

实测 `crmDbService.ts` 中**零事件写**：

```
$ grep -c "customerEventAdd\|INSERT INTO customer_event\|UPDATE customer_event\|DELETE FROM customer_event" electron/services/crmDbService.ts
0
```

**定性**：行为**没有**变更（crmDbService 始终零事件写），坏的是**断言的匹配口径** → 归 **(c) 测试本身坏**，非 (a)。（另一种读法是「注释是刻意加的所以算 (a)」；但 (a) 的定义是「**行为**有意变更」，注释不构成行为变更，故仍判 (c)。）

**处置（c 类）**：断言**改锚定「写形态」** —— 只有真正的写才命中：

```ts
!/customerEventAdd|customerEventUpdate|customerEventDelete|INSERT\s+INTO\s+customer_event|UPDATE\s+customer_event|DELETE\s+FROM\s+customer_event/i
```

**等价强度**：语义（「crmDbService 零事件写」）**一字未改**；匹配范围从「任意提及」收窄到「写形态」，**排除了原本的假阳性**，对真正的写入覆盖反而更精确（原正则漏掉的大小写/空白变体现在被 `i` + `\s+` 覆盖）。

### 2.5 `scripts/crm-logistics-test.ts` — (b) 真实回归（已按批准恢复代码）

**症状**：启动即死于 line 89，抛 `请选择具体待办；不能按客户批量完成`。

**根因**：**W2a 重写 `completeUnifiedSignal` 时整段删掉了 `logi:` 分支**。原分支（`c325179^` 版本）：

```ts
if (String(sessionId || '').startsWith('logi:')) {
  const logisticsId = Number(String(sessionId).slice(5))
  const tasks = salesDbService.todoList({ status: 'pending', session_id: sessionId, limit: 20 })
  for (const t of tasks) if (t.id) completeAction(t.id, action)
  if (action === 'done' && logisticsId > 0) crmDbService.markLogisticsSigned(logisticsId, { actor: '今日行动' })
  return
}
```

删掉后，`logi:<id>` 卡走到 `todo:` 前缀判断 → 不匹配 → `id` 落 0 → 抛守卫。**今日行动与确认中心两个入口都关不掉物流超期卡**，且错误被前端空 `catch` 静默吞掉（无任何提示）。

**这是守卫「误伤合法调用」，但守卫文本本身是对的** —— 两者必须分开处理：

- 守卫（拒绝按**客户**批量完成）**保留不动**；
- 缺的是 `logi:` 这条**独立分支**（指向一条**物流记录**，不是客户会话）。

`docs/规划/两份优化方案收口计划-20260912.md` §1.3 已把此定性为**真实回归**并给出正解；§1.3.1 论证了**恢复该分支不与 W2a 禁令冲突**：

1. **「不能按客户批量完成」**射程是**客户**会话 —— `todo:<customerId>` 一张卡会扫掉该客户名下互不相关的待办；`logi:<id>` 指向**一条物流记录**，其下待办同属一件事（同一 `trigger_type`），关掉它们 = 关掉这一件事。
2. **`:957` 对 R8 + done 的拒绝**（「请到物流记录确认签收」）理由在此**已被满足而非被绕过** —— `logi:` 卡**本身就是那个签收入口**，其 done 语义就是 `markLogisticsSigned`。

**处置（b 类：修代码）**：经用户确认后，**取最小修复** —— 仅恢复 `logi:` 分支（未一并做 §1.3 的「签收钩子」，见 §7 遗留项）。恢复位置在 `action` 校验之后、`id` 计算之前（与 `c325179^` 的次序一致），并补注释写明出处与不冲突论证。

`markLogisticsSigned` 本身幂等（已 `signed` 直接返回 `ok:true`），故测试 §4 的「重复完成幂等」与「skipped 不标记签收」无需额外处理即通过。
