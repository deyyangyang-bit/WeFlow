原设计（§2.x「非客户自动黑名单」）：AI 输出【阶段=未知】→ `blacklistNonCustomer` 自动把该会话写入 `aiInsightNonCustomerBlacklist` → `isSessionAllowed` 先查黑名单硬屏蔽。**该自动写入链路已在 AI 简报改造（§1.x）中随 `applyParsedStageSignal` 降级一并删除**，但配置键、类型、设置页 UI 与「非客户」语义全部沿用至今——留下一个**没有任何写入方、却仍能屏蔽用户**的名单。本刀把它重定义为纯手动管理的「AI 见解屏蔽名单」。

约束照旧：不 `git commit`、不 `git push`，工作区其他任务的未提交改动不回退不清理，本刀改动叠加其上。用户已拍板三项，直接照做：① 手动单客户显式触发绕过屏蔽；② 「加入名单」入口放客户工作台「…」菜单并带二次确认；③ 存量条目全部视为旧版自动判定产物。

#### 1. ⚠️ 开工核实：任务前提被证伪（两处，均影响改动面）

开工单描述「手动单客户触发也走这道闸门，批量触发仍受挡」。**核对源码后两句话都与事实不符**，因此闸门是**新增**的，不是修改既有拦截：

| 说法 | 核实结论 | 证据 |
| --- | --- | --- |
| 手动单客户触发受闸门挡 | **否**——`isSessionAllowed` 全仓**只有 1 个调用点**，在 `triggerTest()` 选会话处（只决定「挑哪个私聊做测试」）。`triggerSessionInsight`（`ChatPage.tsx:6711` 手动入口）与 `batchProfileCore` **都不调用它** | `isSessionAllowed` 调用点：`insightService.ts:419` 一处；`generateInsightForSession` 内无 |
| 批量触发已受挡 | **否**——批量画像 `batchProfileCore` 直接进 `generateInsightForSession`，**原本完全不受名单约束**。名单此前只在 `triggerTest` 挑会话时生效 | 同上 |
| 「AI 识别这个客户」走闸门 | **否**——`identifyCustomer` → `salesFollowUpService.extractForSession`，该文件 `triggerReason` **零引用**，直接调 `aiApiClient` 并自带游标（`purpose: 'manual_identify' / 'digest'`），**从不经过 `generateInsightForSession`**，因此名单从来没有、现在也没有拦截过识别 | `grep triggerReason electron/services/salesFollowUpService.ts` → 0 命中 |

**对任务开工单第 3 项遗留问题的回答：`extractForSession` 确实不经过 `isSessionAllowed`，其语义等同于「始终绕过」。** 本刀**未**为它补闸门——识别是用户显式单客户动作，按拍板决策①本就应放行；强行给它加闸门反而违背决策①。如实记录，不宣称「已覆盖两条手动路径」。

#### 3. 关键决策落点

| 决策 | 落点 | 说明 |
| --- | --- | --- |
| **判定依据是「触发方式」，不是调用点** | 闸门唯一位置 `generateInsightForSession`，读 `triggerReason` 是否 ∈ `EXPLICIT_MANUAL_TRIGGER_REASONS` | 避开「在每个入口硬编码名单」——那正是原设计失控的成因 |
| 显式手动放行 | `:manual`（`triggerSessionInsight`，`:482`）与 `:test`（`triggerTest`）两条经闸门的手动路径均放行 | 二者都由用户主动点击发起 |
