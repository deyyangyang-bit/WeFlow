> 接手人：Claude Code。范围：§2「⚠️ 疑似真 bug」3 条的逐条核实（先核实再动手）＋ 剩余类型错误清零。
> 结论先行：**3 条中 1 条是真 bug（`messagePushService` 死分支），2 条是类型层误报**（运行期本来就是对的）。
> 同时订正 §2/§3 的一处记录错误：messagePushService 的 2 个 `TS2367` 不在「剩余 7 个」枚举内，
> 编辑前真实存量是 **3 个而非 7 个**。棘轮 `BASELINE` 已由 7 收紧到 **0**。

### 4.1 核实结论（逐条，含运行期/类型层证据）

#### ① `crmIpcHandlers.ts:176` 商机统计 —— ❌ 误报（类型层），运行期不恒 0

- **实际代码形态**（HEAD `677093d`）：不是「整个 `CrmRow[]` 当合计传」，而是
  `activeOpportunitiesByAccount(...).reduce((o, x) => ({ count: o.count + 1, quantity: ..., amount: ... }), { count: 0, quantity: 0, amount: 0 })`
  —— 运行期产出**正确**的 `{count, quantity, amount}`。
- **报错为何看起来像「CrmRow 直接传」**：把该段原样抽到独立探针、用本仓 tsc 实测，得到
  `error TS2345: Argument of type 'CrmRow' is not assignable to parameter of type '{ count: number; quantity: number; amount: number; }'`。
  这条报的是 **`Array.prototype.reduce` 回调累加器形参**的类型（`CrmRow` 的索引签名与合计类型无重叠），
  不是「字段读错」也不是「合计对象被弄错」。原 `CrmRow[]` 数组形态**在 HEAD 上从未存在**。
- **字段名核对**：`opportunity` 表列名就是 `quantity` / `amount`（`opportunityUpsertBySignal` 写入口径一致），
  合计公式 `Number(x.quantity)` / `Number(x.amount)` 与列名一一对应，不存在读错字段。
- **本次改动**：kimi 已把内联 reduce 抽成 `crmDbService.activeOpportunityTotals()`（带显式返回类型，
  消除累加器推断歧义）——**算术逐项等价，零行为变化**。本次另补运行期断言（见 4.3）。
- **顺手修正**：`salesDbService.intentScore` 的 JSDoc 原写「opp 由调用方跨库装配（`activeOpportunitiesByAccount`）」，
  指向的是返回 `CrmRow[]` 的装配器——**这正是本次误读的诱因**，已改为指向 `activeOpportunityTotals`（合计）。

#### ② `crmIpcHandlers.ts:436` 首次分类 reject —— ❌ 误报（类型层），不存在「漏 await」后果

- **实际代码形态**：`enqueueSalesTask(() => rejectFirstClassification(...))`，而
  `rejectFirstClassification` 是**同步**函数（`export function`，第 421 行），返回 `FirstClassifyRunResult`。
- **为何不会有运行期后果**：`enqueueSalesTask` 实现是 `const task = chain.then(() => fn(), () => fn())`
  —— `fn()` 的同步返回值会被 `.then` **自动 adopt** 成 `Promise<FirstClassifyRunResult>`，
  调用方 `async` IPC handler 再把它 flatten 给渲染进程。结果不丢、顺序不变。
  类型层报的是**队列契约不匹配**（`fn: () => Promise<T>` 要求返回 Promise），不是运行时缺陷。
- **现有修法**：`enqueueSalesTask(() => Promise.resolve(rejectFirstClassification(...)))`——**行为完全等价**
  （同一同步调用时机、同一链位置、同一返回值），仅让契约成立。已补注释说明「sql.js runTx 同步落库，包
  Promise.resolve 维持队列契约」。
- **不算「漏 await」的理由**：若真是漏 await，现象会是 reject 结果被吞或队列提前放行；实测（4.3 的 Q7）
  证明队列对同步返回值同样 resolve 到该对象，故无此现象。

#### ③ `messagePushService.ts:1171/1174` —— ✅ **真 bug（真断裂）**，已按真实取值修

- **`getSessions()` 产出的 `type` 真实形态**（静态取证，未猜）：
  - `ChatSession.type: number`（`chatService.ts:27`）；
  - 装配处 `type: parseInt(row.type || '0', 10)`（`chatService.ts:974`、`:1176`）——即 WCDB `Session` 表原始列的
    **数值**，取值只可能是 `0/1/2/...` 或 `NaN`。
  - 因此 `String(parseInt(x))` 只可能是数字串或 `'NaN'`，**永不等于 `'official'` / `'friend'`**。
  - 独立反证：把 HEAD 的 `getSessionType` 原样放进本工程跑 tsc，实测报
    `error TS2367: This comparison appears to be unintentional because the types 'number' and 'string' have no overlap.`
    —— 类型系统独立证明了「两个分支恒不成立」。
- **原写法想表达什么**：`gh_` 前缀判公众号 + `type === 'friend'` 判单聊——这套词汇来自**联系人**的字符串联合类型
  （`chatService.ts:176` `'friend'|'group'|'official'|'former_friend'|'blocked'|'other'`，渲染层
  `SettingsPage.tsx:3703` 就是这么用的）。写法是从联系人类型串到会话类型上的**同名撞车**。
- **因它而死的两条路径**：
  1. SSE 推送 `payload.sessionType`：单聊恒被报成 `'other'`；
  2. `shouldScanMessageBackedSession` 的 `sessionType === 'private'` 提前 return——**「单聊不进消息表兜底扫描」
     静默失效**，单聊被无谓纳入消息表变更触发的兜底扫描。
- **修法**：`getSessionType` 改为**只看 sessionId 形态**（与 `httpService.getApiSessionType` 同口径：
  `@chatroom`→group、`gh_`→official、`@openim`/`weixin*`→other、默认→private；该口径里的 `'channel'`
  在本推送协议无对应值，归入 `'other'`）。不依赖数值语义，故不受 WCDB 列取值变化影响。
- **⚠️ 行为变化（显式列出）**：
  | 项 | 修复前 | 修复后 |
  |---|---|---|
  | SSE `sessionType`（单聊 `wxid_*` / 自定义微信号） | `"other"` | `"private"` |
  | SSE `sessionType`（群聊 / 公众号） | `"group"` / `"official"` | 不变 |
  | SSE `sessionType`（openim、`weixin*`） | `"other"` | 不变 |
  | 单聊是否进消息表兜底扫描 | **是**（跳过分支失效） | **否**（摘要为撤回时仍放行） |
  - 对外契约影响：单聊事件的 `sessionType` 由 `other` 变 `private`，已同步 `docs/HTTP-API.md` §2
    （补 `sessionType` 字段语义 + 修正撤回示例中 `"sessionType":"other"` 的错误样例）。
  - 兜底扫描收紧的**风险评估**：单聊收到新消息必然改动 `unread_count` / `last_timestamp`，
    走 `shouldInspectSession` 正常路径，不依赖消息表兜底；撤回场景由 `isRevokeSessionSummary` 显式放行。
    故收紧不丢推送，只去掉无效扫描。
