## 2. 本轮修掉的两处真实缺陷

### 2.1 `readVersioned` 的 AND/OR 优先级错误（§五）

原实现带一个扫描级附加谓词 `extraWhere`，拼出的 SQL 形如：

```
ts > ? OR (ts = ? AND id > ? AND 谓词)
```

SQL 中 `AND` 优先级高于 `OR`，于是**所有 `updated_at` 晚于水位的行都绕过该谓词出机**。
实测后果：`account.owner_sales` 为空的归属投影照常上行，被中央以 `missing_required:ownerSales`
**永久拒收**，对应 outbox 行永远结算不掉——一条被永久拒收的事件会把队列钉死。

**处置**：「这一行现在能不能投影」属**投影自身的规则**，一律下沉到该投影的 draft 构造
（`ownershipDraftOf`），由扫描与台账 recheck 共用；`extraWhere` 机制整体删除。
修前 `read` 与 `recheck` 对同一行判断不一致，修后二者同源，不再可能一条被拒草稿反复投递。

### 2.2 上行审计投影泄漏原始 wxid（§一）

`maskAuditDetail` 原先只内联了手机号与密钥两类正则，未复用 `maskContact`，导致
`audit_event.detailMasked` 里出现 `{"wxid":"wxid_…"}` 原样出机。

**处置**：改为**字段名驱动 + JSON 感知**的擦洗器——
聊天类字段名整体替换为「本地留存」占位、身份类字段名走 `maskContact`（擦不出内容时整体降级为掩码）、
其余值递归处理并对密钥型键名做正则兜底；字段名谓词直接复用 `shared/centralSync.ts` 新导出的
`isForbiddenChatFieldName` / `isForbiddenIdentityFieldName`，本机与中央**共用同一份禁字段清单**，避免两处漂移。

### 2.3 中央把客户端 4xx 记成 500（§七，附带发现）

缺 `content-type` 的请求体会让 Fastify 抛 `FST_ERR_CTP_INVALID_MEDIA_TYPE`(415)，
而全局错误处理器不看 `statusCode`，一律回 500 并按「中央服务内部错误」记日志——
调用方错误污染服务端监控。**处置**：错误处理器按 `statusCode` 区分请求侧 4xx 与真实 5xx，
日志只对 5xx 记 error；补 `app-test` L1/L2 正反断言。

### 7.2 本轮的两处真实复盘

**其一：`run.pushed` 不能证明「某一行没被重新投递」。** 删掉 J8 的 SQL 翻转后，我最初用
`replayRun.pushed === 0` 断言「已结算的移交行不会再投递」，实测得到 `{"pushed":2,...}`。

`pushed` 是**整轮上行**的计数，不按任何单条 outbox 行计量。改为断言该行两条指令的 `eventId`
**在整轮捕获的请求文本里一次都不出现** + `replayCmds.length === 0` + 行仍 `sent` + 下行/审计计数不变——
这才是「这一行没有被重新投递」的**真实**证据。

**其二：`writeEventFile` 对已存在的路径会跳过，所以补齐后一轮只重写 1 个目标文件（不是 2 个）。**
D 段最初断言 `emitted === 2`，实测 1。核对代码后确认：双目标中只有被隔离的那个目标释放了路径，
另一个目标的文件一直都在队列里（内容本就合法），`writeEventFile` 见路径已存在即跳过。
**这不是缺陷，是既有语义**——断言改为 `emitted === 1`，并在测试里写明原因。

### 8.2 本轮的两处真实复盘

**① 「一致的字段」不等于「一致的事实」。** 第 1 项最危险的地方不是报错，而是**不报错**：
`mode` 与 `sla1Deadline` 类型都对、枚举也合法、审计也干净——只是它们属于**另一条线索**。
第四轮引入的补齐逻辑把「从 assignment 行读回绝对值」当成安全操作，却忘了先问一句
「这行真是这条移交的行吗」。教训：**凡是从本机库回填到对外指令的字段，都必须先证明来源行与指令同指一个业务事实**，
而不是只证明「这行存在」。

**② 状态回读的位置决定了口径。** 第 4 项里 `retryFailedOutbox` 的翻转是**对的**（`failed → pending`
确实发生了，`success:true` 并非谎报），错的是**把「翻转成功」当成了「本行同步成功」**。
整轮 `pushed` 是**所有行**的合计：别的行成功会把它顶上去，网络故障时全都没发出去也**证明不了**
这一行没成功。教训：**单行结果的唯一合法依据是该行自己的最终状态**；用聚合计数反推单行，
无论正推反推都不成立。

## 15. 2026-09-17 销售视图可见性修复（本地署名 ≠ 中央身份）

### 15.1 缺陷一（本轮主诉根因）：归属匹配只认本地署名，中央下行归属被过滤掉

**现象链（全部经代码定位核实）**：绑定中央销售身份的设备，中央合成 assign（seq 930）ACK=applied
且线索已落地，但销售视图看不到；现象报告「改成主管才能看见」。核对结论：该现象成立——
- 落地：`applyDownEventTx` 写 `assignment.sales_name = payload.salesName`（发送侧/中央目录显示名）；
- 过滤：销售视角判定 `isSalesView(identity)`（本地档案 `identityRole='销售'` 且有姓名）后，
  所有可见性口径按 `identity.name === sales_name/owner_sales` 精确匹配；
- 绑定：`claimCentralBinding` 把中央 `displayName/employeeId/role` 存在独立的 `centralSync*` 配置键，
  从不参与视图归属匹配 → 本地署名与中央显示名不同名时，销售恰好看不见「属于自己的」分配。
- 「切主管」是管理视角看全部的绕过，**不是**修复；本轮未按该现象改任何角色权限。

修复口径：归属匹配 = 「本人署名 ∪ 绑定别名」姓名集合（`identityService.getOwnershipAliases()`，
仅中央同步启用且持 employeeId 时返回 `centralSyncDisplayName`；解绑即清），消费点统一走
`shared/ownerFilter.isOwnedName`（新增）——`filterByOwner` / `filterLeadsForView` / `buildMyCards` /
`canClaimLead` / `canBindWxid` / `visibleOwnerChips` / `claimLead` 后端本人判定 / `identity:get` IPC
（新增 `nameAliases`） / hermes 两处。不把 displayName 当永久唯一标识、不用 employeeId 替换姓名
过滤（历史 assignment 只存姓名）、不改 schema、不建第二套身份模型、视角与权限边界不动。

### 15.2 缺陷二：permission_declared 上行必然被真中央拒收（`central_permission` 恒 0）

两处独立契约冲突，均为**代码定位**（非猜测；此前仅凭「central_permission 为 0」不足以定责）：
1. `pushPermissionDeclaration` 发送 `entityId = scopedRef(deviceId, 'permission')`——无 `kind:id`
   具体引用，中央 `/sync/push` 的 `validateCentralEntityId` 必判 `entity_id_not_scoped`（对照中央
   N7 用例以 `permission:1` 形态放行）；本地自检链（A9c）不覆盖该事件（它不经 projection
   selfGuard），假中央测试接受一切，形成「测试绿、生产恒拒」。
2. 中央 `SALES_UPLINK_ENTITY_TYPES` 不含 `permission`（§二.5；I5 用例明确「权限声明不由销售
   设备产生」）——销售角色设备发出的声明即使引用合法也会被 `role_not_allowed_entity:permission`
   拒收，且客户端无终态处理，每轮空试。

修复：entityId 改为具体引用 `<deviceId>/permission:<deviceId>`（businessKey=workspace+entity_id

### 15.3 缺陷三：中央 HTTP recycle 落地解析不到本机 lead（回收被当空操作，lead 滞留）
