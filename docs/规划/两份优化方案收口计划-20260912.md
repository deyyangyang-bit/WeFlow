### 1.3 物流超期卡完成路径失效（真实回归，两个入口）

`completeUnifiedSignal` 在 HEAD 中本有专门的 `logi:` 分支（`git show HEAD:electron/services/salesActionEngine.ts:947-958`，下为节选，原码中 `markLogisticsSigned` 外有 try/catch 并记 WARN 日志）：

```ts
if (String(sessionId || '').startsWith('logi:')) {
  const logisticsId = Number(String(sessionId).slice(5))
  const tasks = salesDbService.todoList({ status: 'pending', session_id: sessionId, limit: 20 })
  for (const t of tasks) if (t.id) completeAction(t.id, action)
  if (action === 'done' && logisticsId > 0) crmDbService.markLogisticsSigned(logisticsId, { actor: '今日行动' })
  return
}
```

W2a 重写该函数为「必须显式 taskId + 拒绝 R8 done」时，**整段删除了 `logi:` 分支**。后果：

1. **今日行动**：`todayActionStore.completeTodo` 对 `logi:` 卡调 `actionCompleteUnified(sessionId, 'done')`，不带 taskId → `sessionId` 不以 `todo:` 开头 → `id` 落 0 → 抛「请选择具体待办」；即便传了 taskId，`salesActionEngine.ts:957` 对 R8 + done 也明确拒绝。两处都抛，且被 store 的 `catch { /* 失败不影响页面 */ }` 静默吞掉 —— **按钮完全失效且无任何提示**。
2. **确认中心**：`CrmReviewPage` 的「确认签收」调 `crm.logisticsSigned`，只改物流状态、不关闭 R8 卡 —— 该缺口在 HEAD 时已存在。
3. 合并后果：签收后 `pendingLogisticsOverdue` 不再返回该单，不会出新卡，**旧卡永久悬在今日行动，无任何入口可关闭**。

**正解**：恢复后端的 `logi:` 分支，保持单一入口、`crm-logistics-test` §4 原样通过；另**新增**签收钩子关闭 R8 卡以覆盖确认中心入口与历史悬卡自愈。**不要**让前端绕路直接调 `crm.logisticsSigned`（那会绕开统一流的任务语义）。

#### 1.3.1 为什么恢复 `logi:` 分支不与 W2a 的禁令冲突

W2a 重写该函数时的两条禁令都需要在此说明为何不适用，否则执行者恢复代码时必然犹豫：

1. **「不能按客户批量完成」**——W2a 的报错原文即为此。禁令射程是**客户**：`todo:<customerId>` 一张卡会把该客户名下互不相关的待办一起关掉。`logi:<id>` 不是客户会话，它指向**一条物流记录**，该 session 下所有待办都是这条记录的 R8 超期提醒（同一 `trigger_type`、同一业务事项），关闭它们等于关闭这一件事，不是扫荡客户。
2. **`:957` 对 R8 + done 的拒绝**（「请到物流记录确认签收」）——该拒绝的理由是「完成 R8 必须去物流记录确认签收」。而 `logi:` 卡**本身就是那个入口**，其 done 语义就是 `markLogisticsSigned`。拒绝理由在此处已被满足，而非被绕过。

未经上述说明直接恢复 HEAD 代码，会被读成「把 W2a 刚禁掉的东西又加回来了」。

#### 1.3.2 HEAD 写法的真实漏洞（本次修复需一并处理）

HEAD 的 session 级扫尾有一个 W2a 之前就存在的缺陷：

- 去重窗口仅 24h（`DEDUP_WINDOW_MS`，`salesActionEngine.ts:119`；判定见 `:474` 的 `hasRecentTask`）。一条物流记录持续未签收满 24h 后，后续每轮扫描都不再被去重挡住，会**随扫描周期不断积累** pending 待办；
- 卡片在 `getUnifiedSignals` 中以 `task:<taskId>` 为键（`:783`），上述多条会**各出一张卡**；
- 前端 `completeTodo` 只传 `sessionId`，于是**点一张卡会关掉两张**——这才是真正接近「批量完成」的场景。

**修复要求**：恢复分支的同时，`completeUnifiedSignal` 接受可选 `taskId` 并按 taskId 精确关闭；前端 `completeTodo` 手上已有 task 对象，应一并传入。session 级扫尾**只保留给确认中心入口**（该入口没有 taskId，且签收本就应关掉这条记录的全部提醒）。

修正前，该方案有三个依次咬合的阻塞，且**没有一个能靠写代码解除**：

1. **§5.4 是观测期，不是编码量**。原文：「数值待实际模型价格及至少 5 个完整工作日基线确定」「这是明确的上线阻塞项」。W1b、W3b、R 都挂在它后面，最短也要 5 个工作日后才能动。
2. **R 的前置未满足**：R 的下游验收、质量/费用对照、回退演练都要求先有 W1b 的预算与批次观测。
3. **W1b 依赖 F2「完整观测」**，而 F2 当前仍有 sla2／payment／旁路调用未打标。

修正后：

| 原阻塞 | 修正后 | 依据 |
|---|---|---|
| §3.2 实时链路待建 | **不建了** | 白天销售自己看得见消息，AI 再报一遍没有价值 |
| §5.4 需 5 工作日基线 | **观测期取消** | 基线是为实时链路定预算用的；实时不做了，基线没有存在理由 |
| W1b 卡在批次设计 | **拆分后只剩游标与共享，可编码** | 删批次，留持久化游标（且因没有实时批次而变得更重要） |
| R 卡在 W1b 观测 | **解除** | R 关掉的正是「白天自动干活」，与新定位同向 |
| F2 需完整观测才能动 W1a | **降为「够用即可」** | 调用量从持续降为「简报每天 1 轮 + 按需」，观测的紧迫性随之下降 |

**净效果**：**块数没变少，变少的是等待。**修正前，9 个未完成块里只有 6 个能开工（F1／F2／F3 收尾、W2b、W3a、W1a），W1b／W3b／R 挂在观测期之后；修正后 9 个全部可开工，**观测期等待归零**。AI 侧本期天花板从「可编码子集 + 观测项显式挂起」变为「可编码子集全部做完」。这次修正解除的是时间约束，不是工作量——工作量近似不变，开工顺序更没有束缚。

诚实的子集划分见 §4。

### 4.3.1 专项：「AI 识别」按钮（新增）

定位修正带来一个新增交付项。设计论证见 `docs/规划/AI见解方案-定位修正-20260912.md` §4，此处只记落地口径。

**先纠正一个事实：今天没有这个按钮。** 核对代码后确认：

- 「AI 识别」是 `trigger_type = 'ai_detected'` 的**显示名**，渲染在散任务卡上（`src/components/sales/TodoSidebar.tsx:15-20,76`）——是标签，不是按钮；
- 真正在「白天自动干活」的是 `electron/services/salesFollowUpService.ts:326-353`：AI 扫聊天记录抽承诺、自动建 `ai_detected`、`created_by: 'ai'` 的待办，**没有人按任何东西**。

所以本项的实质是：**把自动触发改成手动触发，标签保留。** 这与 R（关闭自动评论与预热）是同一条线上的两刀，同批做最省。

**两个入口，两种粒度，成本差一个数量级：**

| 位置 | 粒度 | 文案 | 角色 | 单次成本 |
|---|---|---|---|---|
| 客户 360 / 客户详情页头部 | 单个客户 | 「AI 识别这个客户」 | 主按钮 | **1 次调用** |
| 今日行动页顶部（简报旁） | 全部客户 | 「重新生成简报」 | 次级入口 | N 次调用 |

**为什么主按钮必须在客户页**：① 上班时销售的关注粒度就是一个客户；② 全局需求已被早间简报覆盖，手动重扫是补充；③ **全局按钮点一下等于 N 次调用，可能花掉一天预算，主按钮必须是低成本的——否则销售不敢按，按钮就死了**；④ 客户维度结果直接落到该客户的判断/档案，页面就在旁边。

**落地要求**：

- 状态机完整：空闲／识别中禁用（单飞）／完成／**「没有新发现」**／失败明确报错／额度不足明确阻断。第六项单列，因为同一客户短时间内重复按本来就无事发生，沉默不显示会被读成按钮坏了；
- **产出复用既有 `ai_detected` trigger**，不新建 trigger 类型、不建第二套语义（SSOT：字段语义与对象映射只认 `docs/DATA-CONSTITUTION.md`）；
- `salesFollowUpService` 的抽取逻辑（去重、置信度、`due_days`、优先级）**原样保留**，只换扳机；
- 结果写 `customer_judgment`，有实质进展时生成或更新 `follow_up_task`，**不改正式业务字段**；
- 用量账本 `purpose` 记 `manual_identify`，与后台调用可区分。

**已拍板（2026-09-12，交互口径）**：`created_by` **记操作的销售本人**（trigger 仍为 `ai_detected`，trigger 记来源能力、created_by 记触发人）。其余交互定义——「没有新发现」调用前判定、游标依赖与降级、单飞作用域为全局、全局入口状态机与命名、提额入口——统一见 `AI见解方案-定位修正-20260912.md` §4.7，以该节为准。

**顺带登记的隐患**（本批可一并处理，成本极低）：`ai_detected` 同时是 `follow_up_task.trigger_type` 的**数据库默认值**（`electron/services/salesDbService.ts:270`）。当前所有调用方都显式传了 trigger_type，所以**没有误标**；但将来任何新增调用方漏传，都会被静默标成「AI 识别」。建议把默认值改成中性值或改为非空必填。

**F2 的「价格表」指官方刊例价**（各模型每 token 单价，静态输入），与 §5.4 的「封顶金额」不是同一件事：封顶金额 = 刊例价 × 实测用量。修正后用量从「持续」变为「简报每天 1 轮（⌈活跃会话数/20⌉ 次调用）+ 按需按钮」，可**用粗估起步、按实际调整**，不必等基线——但粗估必须按活跃会话数估简报成本，不能按「每天一两次」估（简报批量扫描本身就不止一两次）。

   **这不是「删一节」，而是推翻一条已写死的原则。** AI 方案 §1.1 有明文：「**不能以减少打扰为由把当天采购进展延迟至次日**」——恰好禁止这次修正做的事。该规则的前提是「AI 是唯一能及时看见进展的角色」，但白天销售就在线上，他当场就看见了；真正会漏的是「人当时没记下来」，而这由「销售直接建手动待办」与「次日简报批量补扫」两条既有通路保障。**这是本次修正唯一一处与原文原则正面冲突的改动**，已在 AI 方案原文顶部加状态提示登记，防止后续 Agent 照原文实施。

   详细记录见 `docs/规划/AI见解方案-定位修正-20260912.md`。**该文档不修改 AI 方案原文，作为其定位修正层并存；实施时以修正文档为准。**

   代价（诚实记录，两项）：

   1. **非工作时段的消息要等到第二天早上**。评估：销售本来不上夜班，真实损失接近零；需要时按 §4.3.1 的按钮手动处理。
   2. **承诺的当天捕获能力**。今天 `salesFollowUpService` 自动扫描，客户说「下周三发货」就当场建卡，销售什么都不用做；改为手动后要等次日简报或销售主动按按钮。这是本次修正最实在的一处能力变化。缓解：早间简报是批量的，不会永久丢失，只是从「当天」变「次日」；且销售本来就能直接建手动待办。**需要观察**：实际有多少承诺是「当天说、当天办」的——若比例显著，说明该加第二个自动时点（如午间），而不是回到全天候实时。

   附带好处：AI 费用从不可预测变为可预测，额度上限不再需要观测期才能定。

   同轮一并记录（**P3/P4，本期不做**）：客户档案后续要录入**腾讯本地部署的 WeKnora 知识库**，客户信息由 AI 从聊天记录抓取后填写。本地部署满足 PRD §7.2.6 的隐私约束；`crmEnrichService` 的提取质量是它的上游。
