## 1. 背景与目标

WeFlow 现状：单机 AI 销售助手（Electron），已具备微信聊天解密存档、客户 360、阶段分类、行动引擎 R0-R8、线索池、跟单中心、关键词知识库等 28 项能力。

**实测基线（2026-09-02 数据库审计）**：被动接收链健康——解析微信消息 5.16 万条、银行到款识别与手动认领运转中、物流签收认领 420 条。主动经营链几乎未运转——4,680 条线索首触仅 1 条、行动卡执行率 0.6%（12,952 张任务卡执行 80 张）、报价 0 / 合同 1 / 商机 5、知识库 219 条零增长。结论：**先把「分配 + 跟进」主动链跑起来，再谈 AI 深化。**

本项目的业务目标（非技术目标）：

1. **客户资源不流失**——资源集中分配、超时回收、离职可交接
2. **跟进不漏**——加好友、首触、回访、拿货、停滞全链路有提醒兜底
3. **知识不依赖老员工**——聊天中的经验经审核沉淀为团队知识
4. **管理看得见**——归属、阶段、成交、报价可追溯

非目标（明确不做）：不替代销售聊天、AI 不自动对外发消息、聊天记录原文不上中央主机、不做通用办公平台。

## 2. 部署拓扑（本项目的地基事实）

**现实拓扑：分散单机 + 多微信号。**

- 每个销售一台电脑，登自己的工作微信；每个销售可能有多个工作微信号
- WeFlow 按微信号分库（现有机制），一台机器可挂多个微信号分库
- 加好友、聊天等检测**只能在销售本机**完成（中央无法感知销售手机上的微信）

因此架构分工为：

```
┌─ 中央主机（独立部署）───────────────────────┐
│  轻量分配服务：资源池表 + 分配/回收/SLA 计时     │
│  （一张表 + 两个接口，非同步引擎）              │
│  后期叠加：PostgreSQL 档案库 / WeKnora 知识库    │
└──────────────────┬──────────────────────────┘
                   │ HTTP API
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     销售甲机    销售乙机    销售丙机
     ├微信号1   ├微信号1
     ├微信号2   └微信号2
     └微信号3
     本机职责：拉取本人分配 / 扫全部微信号分库
     检测加好友 / 上报状态 / AI 建档 / 提醒执行
```

**铁律：计时与裁决在中央，检测与执行在本地。** 中央服务只有分配域，不构成对销售机的实时运行依赖（中央主机离线时销售端照常工作，状态恢复后补报）。

## 3. 角色与权限总表

| 角色 | 客户数据 | 资源分配 | 知识库 | 成本价 | 治理操作 |
|---|---|---|---|---|---|
| 销售 | 本人客户全部（多微信号归并） | ❌ 只读本人分配情况 | 读已发布 | ❌ | 提提案 |
| 分配员（权限组，默认主管兼任） | 同主管 | ✅ 录入/分配/调比例/回收 | 同主管 | 同主管 | — |
| 销售主管 | 团队只读（阶段与成交，**不看聊天原文**） | ✅ | 读 + 审核 | ✅ | 审核/移交审批/仲裁 |
| 管理员 | 归属管理 | ✅ + 规则配置 | 全部 | ✅ | 账号/角色/密钥 |
| 系统/AI 账号 | 仅经 Tool Gateway 按调用者身份 | ❌ 永不授予 | 禁发布 | 受 ACL | 无人工登录 |

### 3.1 身份认证分层（不做传统登录界面）

| 层 | 阶段 | 形态 | 状态 |
|---|---|---|---|
| 防窥探 | 已有 | 应用锁（密码锁屏，`LockScreen` + 设置页开关 + 侧边栏一键锁定） | ✅ 已实现，单机自管，离职交接改密码即可，无中央回收负担 |
| 员工身份 | Phase 1 | **本地身份档案**（需求项 1.2a），非登录界面 | 待开发 |
| 企业认证 | Phase 3a | **中央主机工作区绑定**（见 Phase 3a） | 待开发 |

**为什么 wxid ≠ 员工身份**：一人多号（3 个 wxid 同一人）、换号（wxid 变了人没变）、离职交接（wxid 没变人变了）。wxid 只作设备/数据源标识，员工身份独立建档。

## 4. Phase 0 · 数据宪法（1~2 周）

### 交付物

`DATA-CONSTITUTION.md` + 建表 DDL + 迁移脚本骨架。**本阶段不含存量数据迁移**（迁移属 Phase 1 第一周）。

### 内容范围

- 11 个核心对象：`customer / customer_identity / lead / assignment / ownership / ownership_history / stage_history / evidence / outbox_event / audit_event / opportunity`
- `quote`（报价）直接入宪——Phase 1 报价版本管理要用
- `action / ticket` 列为"扩展对象"，入宪时机：Phase 2 / Phase 4
- 两项 Policy：Identity Resolution（手机号优先 / wxid 兜底 / 后补关联；AI 只可提合并提案）；Stage Transition（允许跳级、回退受限、成交禁直连、流失复活需确认）
- SSOT 规则 + Soft Delete 规则 + Feature Gate 七问，同步写入仓库 `AGENTS.md` 铁律区
- AI 字段三档：A 类 auto_committed（依据 = 证据质量 + 规则校验，LLM 置信度仅辅助）/ B 类 proposed→confirmed / C 类 request→审批

### 验收标准（DoD）

1. 11+1 对象 DDL 评审通过，字段含 source / updated_by / updated_at / version / 删除标记
2. 销售主管确认 Identity / Ownership 两章符合业务实际
3. 契约导入现有库成功（空表结构可建）
4. `AGENTS.md` 铁律区更新完成

## 5. Phase 1 · 单机可靠性（约 3 周，重排后）

> 原 2 周估算不现实，重排为 3 周并排序：备份 → 迁移 → 分配 → 售后规则。

### 需求项

| # | 需求 | 要点 |
|---|---|---|
| 1.1 | **自动备份**（第一优先级） | 本机双库加密备份 → 中央主机（未就位前：外接硬盘/另一台机，改路径切换）。每日增量 + 每周全量；恢复演练一次 |
| 1.2 | **存量数据迁移** | 现有客户/线索/历史成交映射进 11 对象；待导入的存量线索（含奋斗群批量线索约 4,281 条）走查重后进资源池；迁移报告（成功/失败/冲突数） |
| 1.2a | **本地身份档案**（分配前置） | 首次启动/设置页建立：姓名 + 角色（销售/主管/分配员），存本地配置，与现有应用锁完全独立。用途：`audit_event` actor 署名、分配服务认领身份、审批确认显示操作人。**⚠️ 角色字段仅作署名，不作访问控制依据**（Phase 1 自我声明即使填主管也无团队数据可看——数据按微信号分库，池子与分配台在分配端机器上；真正权限闸门 = Phase 3a 中央主机服务端绑定认证，主管/分配员/管理员多一步验证）。Phase 3a 绑定中央主机时平滑升级为企业账号，档案字段不变 |
| 1.3 | **客户资源分配** | 分配员录入（Excel/粘贴导入、自动查重）→ 三模式分配（比例权重默认/轮询/负载）→ 销售机拉取 → 两段接力 SLA → 回收改派。4,281 条群扫线索只有昵称/联系方式、无客户名称资料：**先小批量试分配（约 200 条）验证可加率与首触率，达标再放量；不达标先补数据质量，不整批下发** |
| 1.4 | 两段接力 SLA | 第一段"加了没有"：分配后 24h 未加好友 → 提醒，每 24h 复查，第 3 次抄送主管，3 次后回收改派他人。第二段"聊了没有"：**弃用首触 SLA 计时器，改为 LLM 扫描对话判断跟进状态**（是否已有效触达 / 是否需介入），低置信转人工；第一段"加了没有"无对话可扫，保留机械计时 + 检测 |
| 1.4a | 加好友判定（双路） | ① 自动：本机扫全部微信号分库匹配手机号/wxid；② 手动：销售在资源卡「绑定微信」——昵称关键词搜索 → 下拉选本机联系人（多微信号分库合集）→ 确认。内部绑 wxid（昵称仅显示用，改名不失效）。任一命中即停表。绑定写入 customer_identity（source=manual, confidence=1.0），全程审计留痕 |
| 1.5 | 客户类型字段 | dealer / end_user，R9/R10 的前置 |
| 1.6 | 售后生命周期 | 每笔成交独立走：成交 → 已交付 → 待回访 → 复购/老客（规则驱动）；复购客户叠加客户级关系维护（升 A 级、回访频率提高） |
| 1.7 | R9/R10/R11 | R9 经销商拿货（签收第 10 天预警，15 天 deadline）；R10 回访（成交后 15/30/90 天，与 R5 沉默唤醒互斥——已成交客户不走 R5）；R11 阶段停滞（比价>14 天/决策>21 天，纳入统一去重压制） |
| 1.7a | 设备级周期提醒 | 按交付日期起算：电池健康/更换（锂电 3-5 年）/ 轮子磨损（PU/尼龙轮 6-12 个月）/ 液压起升系统检查 / 改装件质保到期 / 以旧换新信号。**注意：本产品为非特种设备（电动托盘搬运车、手动改电动），无年检类提醒** |
| 1.7b | R12 经销商拿货周期预警 | 简单版：经销商 60 天未拿货 → 提醒主动联系；学习版（按历史拿货间隔个性化）进 Phase 4 |
| 1.8 | 成交登记 + 报价版本 | 成交额/型号/数量/交期落字段；报价带版本/生效期/证据链（字段级规格见 5.1） |
| 1.9 | owner + 离职移交 | 本地直改 + 批量移交（复用线索移交逻辑） |
| 1.10 | local_outbox | 只记录不发送，含 event_seq / idempotency_key |
| 1.11 | Action Policy 最小版 | priority + dedup 两字段，R 系列统一接入 |
| 1.12 | 对外文档生成（已修复，待打包验证） | 合同 / 报价 / 开票申请按公司真实样板生成。打包态模板路径 bug 已于 2026-09-02 修复：正确加载 resources/crm-templates 真实模板，移除占位模板静默兜底，模板缺失响亮报错。DoD：打包版用真实记录生成三种文档各 1 份，与样板逐项比对一致 |

### 验收标准（DoD）

1. 备份可恢复：随机抽一周备份完整恢复到新机器，数据校验一致
2. 存量迁移成功率 ≥99%，失败逐条有原因
3. 分配全链路在真实数据跑通 ≥20 条：录入 → 分配 → 销售机可见 → 加好友检测 → 首触
4. 回收误判率 ≤5%（抽查回收案例）
5. R9/R10/R11 各产生过真实卡片且无误报投诉
6. 本地身份档案：每台销售机建档完成，分配认领/审批确认/审计记录中的 actor 正确显示姓名 + 角色（非 wxid）

### 5.1 成交登记与报价版本 · 字段级规格

**成交额（多币种）**
- 本位币 = CNY，成交登记以 RMB 结算额为准（业绩/报表统一口径）
- 字段：`amount_cny`（结算额）+ `original_currency`（默认 CNY，手动下拉选）+ `original_amount` + `rate_note`（汇率备注/凭证，如微信支付订单号、回单截图哈希）
- 外贸单以 RMB 结算，外币仅作报价留痕，**不做自动识别与自动换算**

**型号（双层结构）**
- 主型号：强制从产品库主数据下拉选择，禁止手填（打通知识库，支撑复购归因/售后）
- 扩展属性：自由文本（如"含蓝牙模块 V2.1"）；预设标签集后置到 Phase 4 复购信号启用时再做

**数量（双层）**
- `order_qty`（订单数量）：成交时录入，用于业绩核算
- `shipped_qty`（实发数量）：签收环节手动补录（复用物流认领界面加字段）
- 二者差异 >0 自动触发售后跟进任务（接 R9）；扫码签收不做

**交期（区间型）**
- `expected_ship_start / expected_ship_end`，非单一时点
- 聊天中"下周""月底前"等模糊表达：复用 Hermes 档案更新提案管线（AI 抽区间 → proposed → 销售确认生效），不新建 NLP 模块

**交付与设备**
- `delivery_date`（交付日期）：设备级周期提醒（1.7a）的起算基准
- `opportunity.type`：整车 / 改装（手动改电动是独立生意类型）
- 客户现有设备档案：品牌/车龄/是否已改装——改装潜力与以旧换新信号的来源

**报价版本（一单一版）**
- 每笔成交绑定唯一 `quote_version_id`；append-only，历史版本只读不可改
- 版本关联完整证据链：报价单 PDF 哈希（系统 docxtemplater 生成）+ 聊天截图时间戳 + 销售确认操作日志
- 审计事件全链留痕

## 6. Phase 2 · Hermes 与知识治理（约 3~4 周）

### 需求项

| # | 需求 | 要点 |
|---|---|---|
| 2.1 | Hermes MVP | 只做三件：带引用知识问答 / 知识提案 / 确认队列。三段式：触发层 → 工具层（Tool Gateway）→ LLM（aiApiClient）→ 人落锤 |
| 2.2 | 权限链 | User → RBAC → ACL → Tool Permission → Risk → Policy Engine → 执行/审批；高风险（改阶段/移交/发布/对外）必须人工确认 |
| 2.3 | 知识治理 | status / authority / version / TTL + published 过滤 + 审核 Tab + rejected 状态（拒因留档反哺优化）；AI 无 publish 权限 |
| 2.4 | AI 首次分类 | 认领满 24h 触发 + 手动按钮；复用现有分类器/洞察服务；proposed 本机暂存，confirmed 后才可上行。**间接信号提取**：客户不自报家门时，从聊天/昵称/朋友圈/收货地址提取信号（问返点→疑似经销商；"我们冷库"→冷链），带证据出 B 类提案；**信息缺口反问卡**：关键字段缺失时生成行动卡建议销售下次聊天自然提问；证据不足留 unknown（合法状态，不瞎填） |
| 2.5 | 档案持续更新 | 触发：阶段变化/新报价/成交/回访完成/沉默超阈值 → AI 更新提案 → 确认 → 版本+1 |
| 2.6 | 采用率埋点 | 与 Hermes 同天上：Proposal/Knowledge/Action 三类漏斗（generated→viewed→accepted\|modified\|rejected→expired） |
| 2.7 | 冷启动内容包 | 现有话术/FAQ/产品参数官方资料优先；现有 219 条（产品 158 含裸车价 / 话术 59 / FAQ 2，2026-07-29 导入后零增长、无来源与时效字段）只作候选素材，默认 authority=community + staging 待审，人工审核通过才发布；价格类条目与产品库主数据对账，冲突以产品库为准。现有本机知识库不删除、迁移前照常使用；治理版上线后本机库保留为中央主机离线兜底 |
| 2.8 | 审核队列 UX | 批量确认 / 只看 diff / 证据一键跳转；高频 B 类字段支持批量通过 |
| 2.9 | 效果回流 + TTL 巡检 | 知识使用 × 阶段结果归因；知识到期主动问负责人 |
| 2.10 | 商机判定评测（前置门槛） | 现状商机仅 5 条、判定准确率未知。先建标注评测集（≥100 条历史对话，人工标注有无商机与依据片段），基线 P / R 达标后才上线或扩展判定场景；评测集随 Phase 0 evidence 结构落库，可复用现有商机记录回溯标注 |

## 11. ADR-001：弃用 Twenty CRM 底座

**背景**：早期 PRD（团队版）曾选型 Twenty 作为 CRM 底座。

**决定**：弃用 Twenty，企业事实层自研（中央主机 PostgreSQL + 轻量同步）。

**理由**：
1. **数据生产方式不同**——Twenty 是表单驱动 CRM（销售手动填卡）；本项目核心是聊天驱动（AI 从聊天自动建档）。让销售填两遍表等于杀死系统最大卖点。
2. **违反 SSOT**——Twenty 会携带自己的客户/阶段模型，与 WeFlow 本地事实形成第二事实源。
3. **不解决真难点**——本项目难在单机节点 + 离线可用 + 事件同步，Twenty 均不覆盖，引入后这些仍需自研，反而多套系统要维护。

**后果**：企业层需自研（已计入 Phase 3a 工作量）；团队版 PRD 文档归档标注"已被 ADR-001 取代"。

### 13.1 中央节点采购策略（阶段一主机 / 阶段二按需升 NAS）

**阶段一 · 独立主机（当前方案，Phase 3 起用）**

- **形态**：本次基线为 x86-64 商用迷你主机，二手可选；核验具体 SKU、成色、散热与盘位配件，不以体积推断可靠性。
- **规格**：内存 ≥16GB（推荐 32GB）/ Docker / ≥2 个内部存储盘位（双 M.2 或 M.2 + 2.5″）/ 两块等容量 SSD / 千兆起步，2.5G 可选。单盘位不纳入本次采购。
- **四项上线保护**（与 R3 一致，主机与 NAS 均须验收）：① 镜像及单盘独立启动；② UPS 与断电/来电恢复；③ 一致性加密备份、异地副本与异机恢复；④ 本机监测与外部心跳告警。RAID 不替代备份，NAS 也需另配 UPS 并配置保护措施。
- **就位节点**：不晚于 Phase 2 结束；采购、自建与 Phase 2 并行。D1/D2/D3 下单前落实，D4/D5 与恢复目标上线前落实，细节见采购方案 §8/§9。

**阶段二 · 视情况升 NAS（非必须）**

- **触发条件**：需要热插拔、厂商支持或更易维护的存储管理；盘位不足或实测资源/恢复目标不达标时，比较扩容、换主机与 NAS。人数增长只触发复评，不直接决定采购。
- **运维条件**：始终须有内部责任人或外部维护服务。无人运维不得上线，不能通过换 NAS 豁免应用、数据库和恢复责任。
- **迁移边界**：主机 → NAS 保留已有 API/事件契约，通常只换部署与连接地址；Phase 1 SMB → Phase 3a 内网 API 是独立的软件演进，权限、冲突裁决与同步范围仍按 Phase 3a 实施。
- **迁移路径**：预演 → 旧节点停写并冻结后台任务 → 最终一致性备份/恢复（含文件、队列与去重状态）→ 校验 → 隔离旧写者后切换 → 积压重放验证。新节点开放写入后，回退须先停写并逆向恢复最新数据，禁止直接切回旧库。详见采购方案 §5。
- **架构**：arm64 为替代方案，须验证锁定版本的全部容器与数据库扩展；不能由主应用镜像支持情况推断整栈兼容。

**实施细节**（机型 / 盘位 / UPS / 备份拓扑 / 上线检查单）见 [中央节点采购方案](中央节点采购方案.md)。
