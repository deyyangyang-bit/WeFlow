# 中央节点采购方案（阶段一：独立主机）

> 上级依据：`weflow-hermes-PRD-v3.4.md` §13.1「中央节点采购策略」。本文只写采购与部署怎么做，不重复需求。
> 状态：待采购决策（预算与场地见 §8 未决事项）
> 日期：2026-09-12
> 复核修订：补齐一致性备份、单盘启动、外部告警和停写迁移要求。本文是实施与验收规范，尚未装机演练；业务待定项见 §8。

---

## 1. 目标与边界

**要解决什么**：Phase 3 起需要一个常在线、数据可恢复的中央节点，承载 PostgreSQL 档案库（3a）与 WeKnora 知识库（3b）。

**不解决什么**：不承载聊天原文（PRD 非目标明确不上行）；不作为销售机的实时依赖（PRD §2 铁律：中央离线时销售端照常工作）。

**因此本节点的核心指标不是性能，是两件事**：① **常在线**；② **在约定的数据损失与恢复时间范围内可恢复**（目标见 §3.2，待业务确认）。

## 2. 阶段一规格（硬性）

| 项 | 要求 | 说明 |
|---|---|---|
| 形态 | **x86 商用迷你主机**（1L 级） | 优先便于办公场地放置的商用机；按实测功耗、噪音、散热与维护条件验收，不以体积代替可靠性判断 |
| 内存 | **≥16GB，推荐 32GB** | WeKnora 官方最低 4GB / 推荐 8GB；PRD 取 ≥16GB 是给 PostgreSQL + 向量索引 + 备份任务留余量 |
| 存储 | **≥2 个内部存储盘位**（双 M.2 或 M.2 + 2.5″） | 双盘位是冗余的最低门槛，单盘位机型直接排除 |
| CPU | 具体 CPU 随配置单核验，不以“近三代”为硬门槛 | 按实际容器组合验证资源余量；本方案不含本地模型推理与 GPU |
| 网络 | 千兆起步，**2.5G 可后加** | 内网同步不是带宽瓶颈；2.5G 属加分项非门槛 |
| 系统 | Linux（Debian/Ubuntu LTS） | Docker + PostgreSQL + ZFS/mdadm 生态最省事 |
| 架构 | 本次基线为 x86-64 | arm64 属替代方案，须逐一核验锁定版本的全部依赖镜像与扩展，不能由主应用镜像推断整栈兼容 |

**选择理由**：二手商用迷你机可作为控制初期投入的候选。二手成色、散热、盘位配件和保修差异须逐台核实；不承诺统一的 7×24 认证、固定功耗或相对 NAS 性能倍数。

**候选机型**（按可获得性排序，均为 1L 商用机）：

| 机型 | 盘位 | 内存上限 | 备注 |
|---|---|---|---|
| Dell OptiPlex Micro 7060 / 7070 | 1×M.2 + 1×2.5″ | 32-64GB | 二手市场量大 |
| Lenovo ThinkCentre M720q / M920q | 1×M.2 + 1×2.5″ | 32-64GB | Homelab 社区保有量高，资料多 |
| HP EliteDesk 800 G4 / G5 Mini | 1-2×M.2 + 1×2.5″ | 32-64GB | 部分型号支持双 M.2 |
| N100 / N305 全新迷你机 | 多为单 M.2 | 16-32GB | 更省电，但**盘位常不足，选型时先确认** |

⚠️ **下单选型前必须确认该具体型号的盘位实物图**——同系列不同 SKU 盘位差异很大，同时确认供电、转接线、硬盘托架和散热空间齐全；单盘位不符合本方案。

## 3. 存储与冗余方案（主机不自带，必须自建）

### 3.1 内部：双盘 RAID1 镜像

**基线为 mdadm RAID1**：两块等容量 SSD，系统根卷与数据卷纳入镜像；可用容量按较小盘计算，并扣除引导分区与文件系统开销。加密卷的解锁方式及恢复密钥须与无人值守启动方案一起验收，不能只完成加密却无法来电恢复。M.2 + SATA SSD 的写入性能受较慢设备约束，不能把 SATA SSD 的性能数字用于 HDD。预算中的副盘也必须是 SSD。

- 两盘各自配置可启动的 EFI 分区与引导程序，明确引导文件更新同步流程；根卷镜像不等于引导冗余。
- 验收必须分别在“仅连接盘 A”和“仅连接盘 B”时冷启动，确认降级阵列可挂载、服务可用，再执行换盘与重建演练。重建前核对设备序列号，禁止凭易变化的盘符盲目操作。
- 未确认机型支持热插拔时，**关机后拆盘**再开机模拟故障，禁止带电拔内部 M.2/SATA 盘。
- 单盘位机型不采购，删除以每日 rsync 代替镜像的退路。RAID1 只缓解单盘故障，不防误删、勒索、整机损坏，也不替代备份。
- 若改用 ZFS mirror，须另补系统引导和恢复步骤，并用 `zpool status` 验证；不得用 `/proc/mdstat` 验收 ZFS。

### 3.2 外部：日常备份目的地

**待确认的服务目标**：在成功备份且副本可用的条件下，本地恢复 RPO（最多丢失的数据时间）≤24 小时、RTO（恢复服务时长）≤1 个工作日；当前只是规划目标，须以演练结果确认。异地恢复目标由 D4 决定；若业务要求分钟级 RPO，需另配 WAL 归档/PITR，不宣称日备份可以达到。

| 层 | 介质与方式 | 频率 | 保留 |
|---|---|---|---|
| 单盘故障容错 | 内部 RAID1 | 实时镜像 | 不作为备份副本 |
| 本地版本备份 | 外接 USB 硬盘上的 restic 加密仓库 | 每日一次；文件块去重增量 | 最近 30 个日版本及 12 个周版本 |
| 异地副本 | 独立场地或云端加密仓库 | D4 定频率 | D4 定保留期与恢复目标 |

**每日备份流程（上线前落成脚本与 systemd timer）**：

1. 校验 USB 盘 UUID、挂载点与剩余容量，未挂载直接失败告警，不写入系统盘上的同名空目录。
2. 暂停中央写入入口、定时写任务和 WeKnora 导入/索引任务，等待在途事务与后台任务结束；终端继续本地工作并暂存上行事件。保持停写直至数据库及关联文件采集完成。
3. 对业务 PostgreSQL 与 WeKnora PostgreSQL 分别执行 `pg_dump -Fc`，另导出恢复所需角色/权限；记录数据库、扩展、镜像版本。这里是**每日数据库逻辑全量**，不是 PostgreSQL 原生增量。
4. 同一停写窗口采集 WeKnora 原始文件、实际启用的对象存储/向量存储和持久队列。按选定组件的官方备份方式导出；没有在线一致性方案时停服务后采集。建立组件清单，明确哪些可重建、如何重建及耗时。禁止直接 rsync 运行中的 PostgreSQL 数据目录或无一致性保证的数据卷。
5. 生成含时间、组件、文件校验和、版本与恢复顺序的清单；采集完整后恢复写入。临时导出目录仅备份账号可读且位于加密文件系统，随后写入 restic 仓库；只有仓库成功完成才记为成功备份，完成后清理临时产物。
6. 每周检查仓库结构与数据完整性，按固定主机/路径分组执行保留策略（30 日版本、12 周版本；清理前 dry-run 核对）；上线前以及备份格式/组件版本变化后，恢复至隔离实例并验证业务记录、文件引用、知识检索与事件去重。记录耗时和最新可恢复时间；备份失败或超过 24 小时无成功备份主动告警。

**密钥与灾难恢复**：中央节点使用独立的 restic 仓库密钥，经受限 secret 文件（仅服务账号可读，权限 600，父目录 700）或 secret 管理服务注入。禁止硬编码、提交 Git 或输出日志。环境变量只是传递方式，不是密钥备份。仓库密钥、必要凭证及恢复说明另存受控密码库/离线介质，并验证在原主机不可用时能够取回和解密。

销售端既有双库备份使用 `autoBackupKeyVault` 的 safeStorage/local-wrap 封装，不改成环境变量方案，也不与中央仓库共用密钥。接收销售端备份时按终端隔离目录、配置访问控制，并保留其已有恢复材料。

异地副本必须在上线前按 D4 配置并完成恢复抽查；同机镜像和长期连接的 USB 盘不能覆盖整机失窃或场地损毁。容量按真实首轮备份量、变化量与保留期计算，2–4TB 仅为预算候选。

### 3.3 断电保护（UPS）

| 项 | 要求 |
|---|---|
| 容量 | ≥500VA / 300W（按主机、外接盘及必要网络设备的实测负载和所需关机时间核算续航） |
| 接口 | 本方案优先 USB HID；下单前核验具体 UPS 型号与 NUT 驱动兼容，不把普通 USB 接口当作兼容证明 |
| 软件 | `nut`（Network UPS Tools）：断电触发延时后自动优雅关机 |
| 必测 | §9 检查单的「拔电演练」——**不测等于没配** |

**断电与来电恢复**：UPS 是降低突然掉电风险的额外保护，不能代替 PostgreSQL WAL/正常持久化配置；本项目 sql.js 截断写事故不等于 PostgreSQL 的故障机制。演练需覆盖断电关机、来电重启、短时停电后恢复，以及 UPS 尚未断输出时主机已关机的情况。核验 BIOS 来电策略、NUT 关机/断输出联动、Docker 自启动和服务健康；无法自动恢复的情况须记录人工操作人与响应时限。

## 4. 软件栈

```
Linux (Debian/Ubuntu LTS)
├─ mdadm RAID1                    ← §3.1
├─ Docker + Compose
│   ├─ PostgreSQL                 ← Phase 3a 档案库
│   └─ WeKnora（按锁定版本与启用 profile 列组件清单） ← Phase 3b 知识底座
├─ nut                            ← §3.3 UPS 联动
├─ smartmontools (smartd)         ← 磁盘 SMART 预警
└─ 备份任务（cron/systemd timer）  ← §3.2
```

**部署清单**：固定 OS、Compose、镜像版本或摘要以及启用的 profile，禁止生产依赖 `latest`。本地 `WeKnora/docker-compose.yml` 包含独立 PostgreSQL、Redis 及多种可选存储，实际启用项逐一登记其数据卷、备份和恢复方法；业务库与 WeKnora 库分开管理，不假定一个普通 PostgreSQL 镜像满足所有扩展。

**凭证管理**：按 §3.2 使用受限 secret；环境变量可作为服务注入接口，不把包含秘密的 `.env` 当作安全存储。配置模板入库，实际凭证不入库；记录凭证轮换与异机恢复流程。

**告警出口**：本机监测 SMART、RAID 降级/重建、磁盘空间、PostgreSQL 与备份状态；另在其他设备或外部服务运行心跳检查（建议每分钟检查，连续 5 分钟无心跳告警）。外部检查不依赖被监测主机及其应用推送服务。D5 指定接收人、备用接收人和响应时限，D3 指定处理人。复用 Phase 2 通道仅限其依赖独立且演练通过的情况。

## 5. 阶段二：升级 NAS 的触发条件与路径

**触发条件**（任一成立再评估，非必须升级）：

- 需要通过 NAS 管理界面减少存储维护工作，且已有内部责任人或外部维护服务
- 需要热插拔盘位与厂商级支持
- 实际容量、并发或恢复演练结果不满足目标（人数增长仅触发复评，不直接决定换 NAS）
- 盘位不足；性能不足时比较扩内存/存储、换主机与 NAS 的实测结果，不假定 NAS 更快

**无人运维不能靠换 NAS 解决**：D3 未落实则不接入生产。NAS 同样需要数据库、应用、备份、升级与故障处理责任人。UPS 需另配，RAID 和通知也需配置验收。

**迁移边界**：阶段一主机迁至 NAS 时保留已有 API 与业务事件契约，通常只换部署位置和连接地址，不要求换传输 adapter。Phase 1 的 SMB → Phase 3a HTTP API 是另一次软件演进；权限、冲突裁决与新事件仍须按 Phase 3a 契约实施，不能算作硬件替换已完成。

**迁移步骤（预演通过后安排维护窗口）**：

1. 锁定新旧组件版本、数据库扩展和架构兼容性，在新节点完整预演恢复，记录停机预算；跨架构不直接复制数据库物理卷。
2. 暂停旧中央节点所有写入口、同步消费/投递、后台任务和 WeKnora 写入，等待在途工作结束；终端本地工作继续，未上行事件保留原幂等键。记录队列、ACK、游标与去重状态，旧节点进入受控只读状态。
3. 在停写状态按 §3.2 采集最终一致性备份，将数据库、文件、必要队列/去重状态和配置恢复到新节点；`pg_dump -Fc` 配合 `pg_restore`，角色与扩展按清单恢复。
4. 校验导出文件校验和、关键表行数与业务抽样、文件引用、知识检索、身份权限和重复事件不重复入账。失败则新节点不开放写入，恢复旧节点服务。
5. 隔离旧节点写入口，切换地址/证书配置，确保只有一个中央写者；恢复新节点后台任务与同步，验证终端积压重放、ACK 结算及离线终端重连。记录正式开放写入时刻。
6. **开放新节点写入后不能直接切回旧库**。回退须再次停写并将新节点的最新一致性数据恢复到旧节点，核对去重/游标后再切换；该逆向恢复须预演。做不到则保持停写修复，禁止丢弃新增数据强行回退。
7. 旧主机保留 ≥1 周且保持写入隔离；观察与恢复验证通过后才降级为备份目的地或退役。保留硬件不代表具备零损失回退能力。
