# 合同抬头样本分布记录（Gate 0）

日期：2026-09-12。对应《合同与报价录入加速-PRD-v1.4》§7.2.6 / §12 Gate 0。

样本来源：用户 2026-09-12 整理的《开票资料汇总（真实样本抬头）》，11 家单位。

> **本文档只记录格式分类与结构特征，不含任何真实税号、账号、电话、地址。** 原始样本为真实客户资料，仅保存在本地，不得进入 Git（PRD §7.2.6 第 4 条）。

---

## 1. 输入口径（本记录的前提）

解析器的输入是**销售粘贴进来的文本**，不是客户原始文件。

实际链路：客户发来 Excel／Word／图片／微信文字 → 销售把其中的文字取出 → 粘贴进系统 → 解析回填。

因此：

- 客户原始文件的版式（Excel 表格、图片排版）**不进入解析器**，由人工在这一步消化；
- 解析器面对的永远是「一段带标签的文本」；
- 本次 11 份样本即为该口径下的真实输入形态，**可直接作为 fixture 依据**。

这同时修正了一个曾被误判的问题：图片类来源**不构成录入缺口**。人工转写环节已存在于既有流程中，解析器只需承接转写后的文本，本期不承诺 OCR，也不需要。

### 关于第 2 项的说明

「六行式／四行式」分类原本用于判断是否值得实现组合标签的自动拆分（PRD §7.2.3 的触发条件是「四行式占比过半」）。按 §1 的输入口径，人工已在此前一步消化了原始版式，该分类对解析器设计不再有决定作用。实测组合标签出现 1/11（9%），**远低于 PRD §7.2.3「占比过半」的阈值**，因此结论与 PRD 现行策略一致：

> **维持「只识别、不自动拆分」——识别到组合标签时提示人工拆分，不猜测字段归属。**

## 3. 样本事实

### 3.1 字段覆盖

| 字段 | 提供家数 |
|---|---|
| 单位名称／纳税人识别号／地址／开户银行／银行账号 | 11 / 11 |
| 电话 | 10 / 11 |
| 联行号（PRD 五字段之外） | 4 / 11 |

### 3.2 标签形态

11 份样本的标签均为「标签: 值」单行形式，标签与值同行、冒号分隔。未出现标签与值分行的情况。

> **设计决策**：PRD §7.2.4 第 9–11 条（标签与值分两行、冒号后为空读下一行、下一行为标签则放弃）在本次样本中**未被触发**。建议**仍然实现**——这三条是低成本防御，且无法保证未来粘贴来源不出现该形态；但不为其编写单独的验收阻塞项。

### 3.3 注记出的格式异常

样本整理时记录的原文特征，构成解析器必须正确处理的行为清单。

| 类型 | 家数 | 表现 | 解析器应有行为 |
|---|---|---|---|
| 组合标签 | 1 | 「开户行及账号」合并为一行 | 命中 comboHits → 提示手工拆分，四个字段均不写入 |
| 字段乱序 | 1 | 账号列在开户行之前 | 逐行独立处理，天然支持 ✅ |
| 非别名标签承载有效值 | 1 | 地址被标注为「项目名称」 | **不命中**，跳过该行（正确的「不猜」后果，地址留空由人工补） |
| 干扰标签 | 2 | 「数字钱包账号」「开票资料」「对公收款」 | 整行完整匹配，均不命中 → 跳过 ✅ |
| 值含人名前缀 | 1 | 电话值前挂联系人姓名 | 原样写入值，由人工核对 |
| 值内分段 | 1 | 税号原文分三段显示 | 见 §4.2 |
| 位数异常 | 2 | 账号 17 位／19 位 | 超出解析器职责，属性来源质量 |

## 4. 冻结的别名表

### 4.1 字段别名（经本次样本验证，不做增删）

| 目标字段 | 标签 | 样本验证 |
|---|---|---|
| `buyerName` | 名称、单位名称、公司名称、客户名称、甲方 | ✅ 命中「单位名称」 |
| `taxNo` | 税号、纳税人识别号、纳税人识别码、统一社会信用代码 | ✅ 命中「纳税人识别号」 |
| `addr` | 地址、单位地址、注册地址 | ✅ 命中「地址」 |
| `phone` | 电话、电话号码、联系电话 | ✅ 命中「电话」 |
| `bank` | 开户银行、开户行、开户行名称、银行 | ✅ 命中「开户银行」 |
| `account` | 账号、帐号、银行账号、银行帐号、开户账号 | ✅ 命中「银行账号」 |

**六个必需字段全部命中，无需修订。** 样本的作用是反向验证别名表充分性。

### 4.2 两项本期决策

**① 联行号（4/11 出现）—— 本期不采集。**

`联行号` 不在别名表中，将作为未识别行跳过。理由：PRD §4.1 定义抬头五项，联行号无落点；落 `custom_fields.liaison_bank_no` 需补契约登记，而文档生成模板使用 `buyer_bank` 等既有键、不读取联行号，采集后无消费方。

> 可逆决策。若后续开票需要联行号，JSON 加键不违反「不新增列」，补契约登记即可。

**② 值内空白 —— 按字段区分（已拍板，PRD 已改）**

原 PRD 规定「值去除首尾空白和 `\r`，保留内部空格、冒号与短横线」。对 `addr`／`bank`（开户行名称含空格属正常）应保留；但 `taxNo`／`account`／`phone` 内部的空白是源格式产物（§3.3「值内分段」一例即为税号被空格分段），保留会把分段值原样回填进合同。

已按下列口径修改 PRD §7.2.4 第 8 条，并在 §10.1 增加对应验收项：

| 字段 | 内部空白处理 |
|---|---|
| `addr`、`bank` | 保留（含普通空格、全角空格、Tab；地址与行名中的空格有意义） |
| `taxNo`、`account`、`phone` | 去除全部空白（含普通空格、Tab、全角空格；口径与 §7.2.4 第 5 条标签侧一致） |

「去除全部空白」显式包含 Tab 与全角空格，与标签侧第 5 条对齐——值侧的税号分段同样可能是全角空格。

§5 用例表的「值内分段（税号含空格）」一行已按此契约编写，无需追加用例。

### 4.3 负面用例（不得命中）

以下标签在真实资料中出现过，必须保持不命中。建议写入回归测试而非别名表：

- `项目名称` —— 曾承载地址，但不得映射到 `addr`（同时印证 PRD §7.2.2「`产品名称`不得命中」的必要性）
- `数字钱包账号` —— 不得命中 `account`（整行完整匹配已挡住）
- `开票资料`、`对公收款` —— 不得命中任何字段
- `联行号` —— 见 §4.2 ①

## 6. 残留风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 人工转写引入误差 | 销售抄错数字，解析器无法发现 | 全部回填字段可编辑；成功提示要求核对（PRD §7.2.5） |
| 非别名标签导致漏字段 | 如「项目名称」承载地址时地址不会被识别 | 已知且接受；字段可编辑，人工补 |
| 值内混入无关文本 | 如电话值带联系人姓名 | 原样写入，人工核对 |
| 组合标签未拆分 | 命中后不写入任何值 | 提示明确，要求手工拆分（PRD §7.2.3） |
