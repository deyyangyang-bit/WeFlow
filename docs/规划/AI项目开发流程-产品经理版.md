# AI 项目开发流程（产品经理视角）

| | |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-09-02 |
| 适用项目 | WeFlow × Hermes（亦可复用于同类 AI + Vibe Coding 项目） |
| 配套文档 | PRD v3.4（需求依据）、开发流程计划 v1.0（工程执行细则） |

> 本文档站在产品经理角度回答一个问题：当开发主力是 AI Agent 时，PM 在每个阶段该做什么、交付什么、凭什么放行。

---

## 1. 为什么 AI 项目需要一套新流程

AI 写代码有三个特征，决定了传统"PRD 往开发一扔"的方式必死：

- **快，但不自律**：不给约束就自由发挥，字段乱建、逻辑绕开规范、功能越写越多。
- **强，但会烂尾**：写个半成品就宣布完成，不测试、不验证。
- **交付快，但验收难**：代码量翻倍，PM 无法逐行审查，传统 Review 方式失效。

因此 PM 的角色必须转变：**从"写需求文档的人"变成"流水线的闸门"**——管好需求边界、验收标准和止损开关，把实现细节交给 AI，把"做不做"和"算不算完"留在人手里。

---

## 2. 流程全景

```
① 需求洞察 → ② PRD 定稿 → ③ 架构与数据契约 → ④ 任务拆解
     ↑                                              ↓
     └────── ⑧ 观测回流 ← ⑦ 发布 ← ⑥ 验收 ← ⑤ AI 开发执行
```

六大阶段对应六个"闸门"，每个闸门都有明确的放行标准（DoD）。**任何一关不过，不进入下一阶段。**

---

## 3. 角色与分工

| 角色 | 由谁担任 | 职责 |
|---|---|---|
| 产品负责人（PM） | 你 | 需求拍板、任务下达、DoD 验收、进度与成本监控、止损决策 |
| 主开发 | AI Agent（多模型分工） | 计划、编码、测试、自验、提交、文档回写 |
| 架构评审 | 专家级模型 + PM | 数据宪法、接口契约、重大技术选型 |
| 业务验收人 | 业务主管 | 业务规则确认、评测集标注、试点反馈 |
| 试点用户 | 1-2 名一线 | 真实环境试用，反馈进 Backlog |

分工铁则：**AI 负责"怎么实现"，人负责"做什么"和"算不算完"。**

---

## 4. 阶段详解

### 阶段一：需求与 PRD（人不许让 AI 代笔拍板）

PM 职责：

- 明确用户是谁、解决什么问题、不做什么（非目标同样重要）
- 用真实数据说话：先跑数据库审计，拿实测基线（例：本项目"线索首触 1/4680、行动卡执行率 0.6%"直接改写了项目优先级）
- 定义业务目标和成功指标，而非功能清单

交付物：PRD（含背景与基线 / 目标与非目标 / 角色权限 / 分阶段需求项 / 每项 DoD / 风险登记 / ROI 基线）

放行标准：业务方确认 + 每条需求有可验证的验收标准。

### 阶段二：架构与数据契约（专家模型主导，PM 主持评审）

PM 职责：不设计架构，但**主持冻结**——没有冻结的契约不许开工。

交付物：数据宪法（核心对象字段级定义、唯一事实源规则、状态转换策略）+ 接口契约（API/MCP 端点级定义）+ 架构图 + 选型决策记录（ADR）

放行标准：契约导入现有库可建空表；业务方确认身份、归属等核心章符合业务实际；铁律写入项目 AGENTS.md。

### 阶段三：任务拆解与下达

PM 职责：把需求项拆成"一个 Agent 一次能完整理解和验证"的任务卡。

任务卡模板（每次下达必带）：

```
任务：<一句话目标>
依据：PRD 需求项 <编号> + 数据宪法 <章节> + 接口契约 <端点>
约束：<不许动的区域 / 必须复用的现有模块>
验收：DoD 第 <n> 条
要求：完成后运行测试并报告所有与规格的偏差
```

放行标准：超过 3 个文件或动数据模型的任务，实现计划必须先经 PM 审批。

### 阶段四：开发执行（AI 自治，PM 不盯过程盯纪律）

执行规则：

- AI 按计划自治执行，偏离计划超过 20% 必须停下重新对齐
- 每完成一个任务立即提交，一次提交只干一件事
- 提交前必须通过类型检查 + 对应模块回归测试
- **验收前不许宣布完成**：必须真实环境跑过、看过结果

PM 盯的只有三件事：进度对不对、纪律守没守、成本超没超。

### 阶段五：测试与验收（机器自验 + 人工验收双层）

- 第一层 AI 自验：类型检查零错误、回归测试全绿、真实数据实测一遍
- 第二层换模型复核：仅对动数据模型、权限、金额的任务启用（主开发模型写，专家模型审）
- 第三层人工验收：PM 对照 DoD 逐条打勾，只看四件事——功能对不对、UI 对不对、操作顺不顺、AI 结果是否符合业务。**不逐行看代码。**

### 阶段六：发布、观测与回流（AI 项目的生死环节）

AI 项目最大的风险不是做错，是**没人用**。发布后必须观测：

- 采用率漏斗：AI 建议生成 → 被查看 → 被采纳 / 修改 / 拒绝 / 过期
- 执行率：行动卡执行率、知识引用次数
- 治理时效：提案待审时长（P50/P90）

观测数据回流到阶段一，驱动下一轮需求排序。**指标不达标先排查（数据 → 埋点 → 口径 → 业务），不许马上改代码。**

---

## 5. 任务分档制度（防止流程压死效率）

不是所有任务都走全流程，按规模分三档：

| 档位 | 标准 | 流程 |
|---|---|---|
| 大活 | 新模块 / 动数据模型 / 动权限 | 全六阶段，契约先行，换模型复核必做 |
| 中活 | 现有模块新功能 | 任务卡 + 计划审批 + 自验 + 人工验收 |
| 小活 | bug 修复 / 文案 / 小调整 | 任务卡 + 自验 + 提交，当日验收 |

---

## 6. AI 协作十条纪律

1. 需求问题人拍板，AI 不替产品做决策
2. 一个业务事实只有一个写入源（SSOT）
3. AI 无发布权：高风险操作（改状态 / 移交 / 发布 / 对外发送）必须人工确认
4. 不顺手做未来阶段的功能，技术上可行 ≠ 现在该做
5. 新需求先过闸门七问：属哪个阶段？为什么现在做？会不会引入未来架构？会不会改数据契约？会不会新增事实源？会不会新增权限边界？挤掉什么？
6. 实现计划超范围必审批
7. 验收前不许宣布完成
8. 一次提交只干一件事，提交信息语义化
9. 文档当天回写，不欠账
10. 通用 AI 纪律框架（如 Superpowers）只是放大器，项目铁律必须写进项目自己的 AGENTS.md——那是唯一保证在场的层

## 7. 质量管理节点

| 节点 | 检查内容 | 判定人 |
|---|---|---|
| 每任务收工 | 类型检查 + 回归测试 + DoD 打勾 | AI 自验 + PM |
| 每周五 | 全系回归 + 周任务对账 + 成本周记 | PM |
| 每阶段出口 | 阶段 DoD 全过 + 评审会 | PM + 业务方 |
| Go/No-Go 门 | 实测指标达标与否 | 管理层评审 |

---

## 8. 成本管理

AI 开发的真实成本不是 API 单价，而是 **Cost / Successful Task**（含 agent 循环、重试、上下文重复注入）。

- 模型分工按实测成本定：主力模型承担 80~90% 开发量，专家模型只上架构与疑难，备用模型按需启用
- 每周记录：任务类型 × 模型 × 成功率 × 实际消耗
- 分工比例每月按实测调整，不为"架构好看"强行分流

---

## 9. 风险与止损

五条暂停规则（触发即停，先对齐再继续）：

1. 要加的字段不在数据契约里 → 停，先修订契约
2. 指标异常 → 按"数据 → 埋点 → 口径 → 业务"顺序排查，最后才动代码
3. 任务连续两次验收不过 → 换模型或缩小任务粒度
4. 现有代码与 PRD 假设不符 → 记录并调整计划，不绕过
5. 出现"顺便做掉未来功能"的冲动 → 过闸门七问，答不过进 Backlog

止损设计：关键阶段设 Go/No-Go 门，不达标则停用新功能、保留已验证资产——止损不是失败，是流程的一部分。

## 10. 文档体系（规格层）

```
docs/
├── PRD/            需求文档（唯一权威需求）
├── architecture/   架构图与说明
├── data-model/     数据宪法（DATA-CONSTITUTION.md）
├── api/            接口契约（API-CONTRACT.md）
├── decisions/      选型决策记录（ADR-001 起编号）
├── tasks/          长任务计划文件（跨会话记忆）
└── HANDOVER.md     全局交接百科
```

配套机制：AGENTS.md 铁律区（永远在上下文里）+ 长任务计划文件（会话中断后读文件续做）。
