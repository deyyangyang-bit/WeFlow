## 1. 背景与问题

当前销售生成一份合同通常需要：

1. 打开合同工作台并新建合同；
2. 手工填写甲方抬头的五个字段；
3. 从产品库选择型号并填写数量；
4. 使用产品库固定单价，无法在当前界面按本次商务条件调整；
5. 创建合同和报价单；
6. 再次触发文档生成；
7. 到 Finder 中寻找生成文件。

主要问题：

- 重复录入：客户经常直接发送完整开票资料，但销售仍需拆成五项手填；
- 改价断点：后端已支持报价单价覆盖，前端没有入口；
- 创建链存在部分成功：新建合同后，报价创建失败会被静默忽略；
- 客户切换存在数据污染风险：从已有客户切回新客户时，旧客户抬头仍可能残留；
- 任务未闭环：系统提示文件路径，但用户仍需自行寻找文件；
- 信息架构偏散：合同列表、详情、报价与文档结果缺少连续操作路径。

## 2. 产品目标

### 2.1 北极星任务

销售从进入合同工作台开始，在同一条流程中创建合同及报价，并直接打开生成文件或定位其所在文件夹。

### 2.2 目标

- 支持粘贴常见甲方抬头文本并确定性回填字段；
- 明确区分“选择已有客户”和“新建客户”，消除客户资料串用；
- 支持逐行调整本次报价单价，并对改价留痕；
- 创建失败时准确说明已完成阶段，并允许从失败点继续；
- 生成成功后提供“打开”和“打开所在文件夹”；
- 保持历史报价 append-only，任何价格变化均创建新版本；
- 在不重构文档模板和数据库结构的前提下完成第一期交付。
- 在编写抬头解析器前，先以真实客户样本校准格式分布和规则，不以原型样例代替业务事实。

### 2.3 建议效果指标

- 标准六字段抬头粘贴后，人工录入次数由 6 次降为 0–2 次核对修改；同一客户第二份合同起无需再次粘贴；
- 已有产品的合同创建流程不超过 1 个主界面和 1 次最终提交；
- 生成成功后打开文件不超过 1 次点击；
- 新客户合同不得继承此前选择客户的抬头字段；
- 报价创建失败不得静默，不得因重试重复创建合同。

## 3. 非目标

- 不新增开票申请单的粘贴流程；
- 不实现“另存为”；
- 不实现发送文件到微信；
- 不引入 AI 或 LLM 解析甲方抬头；
- 不新增数据库表或列；
- 不修改 `custom_fields` 既有键名语义；
- 不修改合同、报价单或开票模板；
- 不改写文档生成核心路径；
- 第一期不为前端组件测试引入新的大型测试框架；
- 第一期不处理 `crmQuoteService.aiGenerateQuotation` 的跨实体原子化，该问题单独立项并与人工创建链统一治理。

## 4. 已有事实与约束

### 4.1 数据落点

甲方单位名称来自 `account.name`。

甲方开票信息使用同一组键名同时落在两处：合同侧是生成文档实际读取的快照，客户侧是新合同默认带出抬头的来源。

| 页面字段 | 数据键 | 本合同快照 | 客户档案复用源 |
|---|---|---|---|
| 单位地址 | `buyer_addr` | `contract.custom_fields` | `account.custom_fields` |
| 开户银行 | `buyer_bank` | `contract.custom_fields` | `account.custom_fields` |
| 银行账号 | `buyer_account` | `contract.custom_fields` | `account.custom_fields` |
| 税号 | `tax_no` | `contract.custom_fields` | `account.custom_fields` |
| 联系电话 | `buyer_phone` | `contract.custom_fields` | `account.custom_fields` |

- `contract.custom_fields` 继续沿用 `crmDocGenCore` 现有键名，不改语义；
- `account.custom_fields` 本期首次写入抬头五项，该列已存在，不新增列；
- 新建流程幂等标识 `creation_request_id` 同样写入 `contract.custom_fields`，不新增列，且不写入客户档案；写入后随合同长期保留，不作为临时键清理。

`contract.custom_fields` 同时承载抬头快照与创建标识，因此所有写入路径必须**合并写入**：

- 禁止整体替换该字段；
- 新增键不得删除或覆盖既有键，尤其不得覆盖已保存的抬头五项；
- 新建合同从空对象构造（新合同无既有键）；合同详情保存抬头时展开既有键后合并，保留其他键。

### 4.2 报价版本约束

- 报价物理实体为 `quotation`；
- 报价采用 append-only 版本链；
- 历史版本只读；
- 价格和行项变化必须通过 `createQuotation` 创建新版本；
- `contract.quote_version_id` 指向当前有效版本；
- `quotation.contract_id` 仅作过渡期双写兼容；
- `createQuotationVersionTx` 被存量迁移逻辑复用，新增参数必须可选。

### 4.3 已有能力

- 后端 `createQuotation` 已接受可选 `unit_price`；
- IPC 已透传报价行项，不需要新增报价 IPC；
- 已存在 `shell.openPath`；
- 文档生成已覆盖合同、报价单、开票信息单和开票申请单；
- 已存在通用 `quote_version_create` 审计事件。

## 6. 核心用户流程

### 6.1 新建合同主流程

1. 用户点击“新建合同”；
2. 选择“已有客户”或“新建客户”；
3. 粘贴甲方抬头，系统立即解析并回填；
4. 用户核对或修改五项开票信息；
5. 搜索产品并添加报价行；
6. 必要时调整本次单价和数量；
7. 系统实时计算报价合计与合同金额；
8. 提交创建；若客户档案与本次抬头存在差异，此时弹出差异确认（§7.1.2）；
9. 系统按阶段执行并展示结果；
10. 生成成功后，用户直接打开文件或打开所在文件夹（生成合同文档属 P2，见 §12）。

> 第 10 步的生成动作在 P0 与 P1 尚不存在，列出完整流程只为说明目标形态。

### 6.2 已有合同补录抬头

1. 用户进入合同详情；
2. 展开“甲方开票信息”；
3. 粘贴完整抬头；
4. 系统回填五项合同字段，不修改客户名称；
5. 用户核对后保存；
6. 后续生成合同或开票文档使用更新后的合同字段。

### 6.3 已有合同创建新报价版本

1. 用户进入合同详情并点击“新建报价单”；
2. 添加产品；
3. 修改本次单价和数量；
4. 系统标出改价行；
5. 提交后创建新的有效报价版本；
6. 上一版本结束生效并保持只读；
7. 改价明细合并写入本次 `quote_version_create` 审计事件。

## 7. 功能需求

### 7.1 客户模式

#### 7.1.1 模式定义

新建合同区必须显式区分：

- 选择已有客户；
- 新建客户。

第一期若沿用现有下拉框，也必须保证 `newAccountId === 0` 时执行完整客户字段重置；第二期改成显式模式切换。

#### 7.1.2 已有客户

- 选择后带出客户名称和可用开票信息；
- 客户名称展示为档案值，不接受粘贴结果覆盖；
- 粘贴出的其他五项信息先回填本合同；
- 客户档案五项抬头均为空时，视为首次建档：直接写入客户档案并提示“抬头已保存到客户档案，下次可自动带出”，不弹确认；
- 客户档案已有抬头、且本次至少一项与档案不同时，在**用户提交创建时**弹出差异确认，不在粘贴瞬间弹出：粘贴后用户还要核对和修改，过早询问会问在未定稿的值上；
- 差异确认逐项列出（字段、档案值、本次值），每项一个勾选框；**默认勾选按字段区分**——`addr`/`phone`/`bank` 默认勾选，`taxNo`/`account` **默认不勾**、需用户主动勾选（防误粘贴串户：单位名称以档案为准，粘错客户在表单不可见，关键字段不能再默认信任本次值）；
- 用户确认后只写入被勾选的字段，未勾选项保持档案原值；全部取消勾选等同于“不更新”；
- 用户选择“不更新”时，只保存为本合同快照，客户档案保持原值；
- 不允许在用户未明确选择时覆盖客户档案；用户直接关闭差异确认视为“不更新”；
- 事务顺序：确认后**先将勾选字段写入客户档案，档案写入失败则中止创建并明确报错**（此时合同尚未创建，无部分成功）；档案写入成功后才执行创建；
- 显示提示：“已选客户，单位名称以客户档案为准；其余抬头信息已自动填写，请核对。”

#### 7.1.3 新建客户

- 客户名称可手工输入；
- `buyerName` 可回填客户名称；
- 合同创建时同步创建 account，并将确认后的五项抬头写入该客户档案；
- 同一客户再次创建合同时，默认从客户档案带出五项抬头，无需重复粘贴；
- 切换到新建客户时，必须清空此前客户带出的名称和五项抬头；
- 合同金额和已选产品不因客户模式切换而清空。

#### 7.1.4 已建合同补录边界

- 给老合同补录或修正抬头时，只更新该合同的 `custom_fields`；
- 不反向更新客户档案，避免将历史合同中的旧资料灌入当前客户档案；
- 若用户需要更新客户档案，应从新建合同流程中的差异确认入口执行。

### 7.2 甲方抬头解析

#### 7.2.1 接口

新增共享纯函数：

```ts
export interface BuyerHeader {
  buyerName?: string
  addr?: string
  bank?: string
  account?: string
  taxNo?: string
  phone?: string
}

/** 命中的组合标签原文及其覆盖字段（§7.2.3） */
export interface ComboHit {
  raw: string
  covers: Array<keyof BuyerHeader>
}

export interface BuyerHeaderParseResult {
  fields: BuyerHeader
  comboHits: ComboHit[]
}

export function parseBuyerHeader(text: string): BuyerHeaderParseResult
```

文件建议：`shared/buyerHeader.ts`。

返回结构要同时承担三件事：

- `fields` 承载六个可回填字段；
- `comboHits` 承载组合标签的原始行与覆盖字段，供“待拆分”提示原样展示（§7.2.5）；
- 两种失败由此可区分，不需要额外标志位：`fields` 全空且 `comboHits` 为空 = 完全未识别；`fields` 全空但 `comboHits` 非空 = 仅命中组合标签。

只返回 `BuyerHeader` 会同时废掉 §7.2.4 第 14 条与 §10.1 的失败区分，实现方会各自补一套私有约定。

#### 7.2.2 别名表

| 目标字段 | 支持标签 |
|---|---|
| `buyerName` | 名称、单位名称、公司名称、客户名称、甲方 |
| `taxNo` | 税号、纳税人识别号、纳税人识别码、统一社会信用代码 |
| `addr` | 地址、单位地址、注册地址 |
| `phone` | 电话、电话号码、联系电话 |
| `bank` | 开户银行、开户行、开户行名称、银行 |
| `account` | 账号、帐号、银行账号、银行帐号、开户账号 |

标签采用整行精确匹配，因此支持标准发票标签“名称”，但“产品名称”等非别名标签不得命中。

#### 7.2.3 组合标签

真实资料中可能出现“地址、电话”“开户行及账号”等组合标签。第一期采取“识别但不猜”的安全策略。

组合标签单独登记为一类别名，与字段别名区分，命中后不写入任何字段值：

| 组合标签 | 覆盖字段 |
|---|---|
| 地址、电话 / 地址及电话 / 地址电话 | `addr` + `phone` |
| 开户行及账号 / 开户银行及账号 / 开户行账号 | `bank` + `account` |

- 识别到组合标签后，不自动拆分值；
- 在对应区域保留原始值；
- 显示提示：“检测到合并字段，请手工拆分后确认。”；
- 不把整段值静默写入地址、电话、开户行或账号中的任意一个字段；
- 组合标签命中不计入“已识别字段数”，不影响解析成功与否的判定；
- 样本统计若显示四行式占比过半，再评审固定规则拆分；
- “开户行及账号”的“末段连续数字作为账号”只作为候选规则，不在样本验证前实现。

#### 7.2.4 确定性算法

1. 使用 `/\r?\n/` 分行并丢弃纯空白行；
2. 每行只查找第一个半角或全角冒号；
3. 冒号前为标签、冒号后为值；
4. 标签长度不超过 12 个字符；
5. 标签去除全部空白，包括普通空格、Tab 和全角空格；
6. 标签必须完整匹配别名，不做包含或模糊推断；
7. 标签命中组合标签别名（§7.2.3）时，记录该行原文与覆盖字段，不写入任何字段值，不计入已识别字段数，继续处理下一行；
8. 值去除首尾空白和 `\r`；内部空白按字段区分处理：
   - `addr`、`bank` 保留内部普通空格、全角空格、Tab、冒号与短横线（地址与开户行名中的空格携带语义）；
   - `taxNo`、`account`、`phone` 去除全部空白，包括普通空格、Tab 和全角空格（口径与第 5 条标签侧一致）。这三类值的内部分段在业务上不携带语义，只会是复制格式的产物，保留会把分段值原样回填进合同；
9. 无冒号且整行匹配标签时，将其标记为等待下一行值；
10. 冒号后为空时，同样允许读取下一行作为值；
11. 下一行如果自身是已知标签（含组合标签），则放弃当前空值且不消费下一行；
12. 每个字段只接受第一个非空值；
13. 未识别行跳过，不报错；
14. 已识别字段数为 0 时视为失败；仅命中组合标签而没有任何字段命中时同样视为失败，提示同时包含未识别与待拆分两种说明。

#### 7.2.5 交互

- 用户粘贴后立即解析；
- 提供“重新识别”和“清空原文”次级操作；
- 解析不会锁定字段，所有回填结果都可编辑；
- 成功提示列出识别到的字段名称，由 `fields` 中的非空键推导；
- 失败提示分两种：`fields` 全空且无组合标签时为“没识别到抬头信息，请手动填写。”；`fields` 全空但命中组合标签时为“没识别到可用的抬头字段，且检测到合并字段，请手工拆分后填写。”——一条提示同时说明未识别与待拆分，与 §7.2.4 第 14 条一致；
- 新建客户时允许回填单位名称；
- 已有客户时忽略单位名称并说明原因；
- 已建合同详情忽略单位名称，提示“单位名称未修改，仍以客户档案为准。”；
- 检测到组合标签时，展示 `comboHits` 中的原始行与覆盖字段，不猜测字段值。

### 7.2.6 真实样本采集门槛

**解析器的输入是销售粘贴进系统的一段文本**，不是客户原始文件（Excel／Word／图片／微信原文）。客户原始版式由销售在粘贴前一步消化，解析器不感知，本期不承诺 OCR。

Gate 0 的采集与统计要求及完成情况（记录见 `docs/规划/合同抬头样本分布.md`）：

| # | 要求 | 完成情况 |
|---|---|---|
| 1 | 从本机微信历史中收集 10–20 份客户真实发送的开票资料 | ✅ 11 份 |
| 2 | 样本仅用于本地开发和规则统计，不上传外部服务 | ✅ |
| 3 | 保存原始换行、全角/半角空格、冒号和尾随空白 | ⚠️ 样本已由人工整理为「标签: 值」规范形态，原始版式未保留（见下方说明） |
| 4 | 对样本做本地脱敏副本后进入测试 fixture，真实税号、账号、电话和地址不得提交到 Git | 📋 规格已定，`scripts/fixtures/buyer-header-real.txt` 待产出 |
| 5 | 按六行式、四行式、其他怪格式统计数量和占比 | ⚠️ 按本版输入口径，该统计对解析器设计无决定作用，未阻塞（见下方说明） |
| 6 | 单独统计组合标签出现次数及具体标签 | ✅ 1/11（9%） |
| 7 | 基于统计结果修订别名表和组合标签策略 | ✅ 六字段全部命中现有别名表，无增删；组合标签维持「只识别、不自动拆分」 |
| 8 | 输出一页样本分布记录，作为解析器开工 Gate | ✅ 已产出 |

**Gate 0 已通过，`parseBuyerHeader` 可开工。**

第 3、5 项的偏差同源于本版的输入口径：客户原始版式不进入解析器，样本由人工在粘贴前一步完成规范化，因此「原始换行」与「六行式／四行式」分布不再影响解析器行为。第 5 项原本用于判断是否实现组合标签自动拆分，其触发阈值（占比过半）已由第 6 项实测结果（9%）明确否定，结论与 §7.2.3 现行策略一致。

### 7.6 部分成功与恢复

第一期不新增跨 account、contract、quotation、文档落盘的统一后端事务。前端保存执行阶段只负责交互连续性；防重复的权威依据必须来自数据库，不得依赖页面内存。

#### 7.6.0 数据库幂等防线

**标识生命周期**

`creation_request_id` 一次新建流程一个。它的职责是让“部分成功之后”还能找回那一份合同，因此清除的是**本地恢复入口**，不是合同上的记录。

- 用户进入新建合同流程时生成，不在打开页面时生成；
- 合同创建成功时写入 `contract.custom_fields`，并**随合同长期保留**：它是这份合同的创建溯源，删除它既无必要，也会与 §4.1 的合并写入纪律冲突；
- 下文所说的“清除”，一律指**丢弃本地草稿、不再恢复该流程**，不是从合同上摘掉这个键；
- 清除触发条件只有两个：整条创建链走完（合同、报价行，以及用户选择生成文档时的文档），或用户点击“取消”/关闭新建区域；
- 再次进入新建流程时，先看有无残留草稿，再按其指向合同的状态分流：
  - 合同不存在或**链未完成** → 恢复该流程，复用原标识与原 `contractId`；
  - 合同存在且**链已完成** → 丢弃草稿、按新流程生成新标识，绝不复用那份合同当作本次创建的结果；
- 恢复动作本身不产生新的标识，因此不存在“同一次恢复被反复触发”的问题。

**最小草稿**

跨刷新恢复只需持久化三项，不保存整张表单：

- `creation_request_id`；
- 当前创建阶段；
- 报价行编辑态。

存放于本地浏览器存储，隔离粒度是**微信账号**（对应现有微信号分库设计，见 `docs/HANDOVER.md` §2.40，一个业务库一份未完成草稿），不是客户：同一微信账号下同时只保留一条未完成的新建流程草稿，切换客户不清空草稿，也不让草稿串到另一个微信账号。本地存储被清空时降级为“同一次会话内有效”，此时按合同列表人工确认，不自动复用。（完整合同草稿的自动保存与恢复仍属后续立项。）

**查询**

- 创建或重试前先按 `creation_request_id` 查询数据库；
- 现有 `crm.list` 只支持合同号、客户号、状态三个等值条件与 `limit/offset`，无法按 `custom_fields` 内的键查询，因此需要新增一个按标识查询的 IPC；
- 查询实现：先用 `LIKE '%"creation_request_id":"<id>"%'` 缩小候选，再解析 JSON 精确比对标识值。不做纯文本精确匹配，因为 JSON 键序和空格不保证稳定，会漏查；也不只用 `LIKE`，因为它会让 `abc` 命中 `abcd`。数据量小，不新增列、不建索引；
- 查询范围限定**当前微信账号的业务库**；
- 已存在合同时复用其 `contractId`，不得再次创建 account 或 contract；
- 创建报价前查询该合同当前是否已有有效报价版本；已存在则跳过创建；
- 生成文档前查询当前记录的附件路径及文件存在状态；已有有效文件则直接展示，缺失才重新生成；
- 页面刷新后通过数据库重新推导已完成阶段；
- 不得使用合同名称、客户名称或短时间窗口做幂等判断，避免合法同名合同被误合并；
- 前端 loading 锁和状态机是辅助防线，数据库查询结果才是最终依据。

#### 7.6.1 报价创建失败

若合同已创建而报价失败：

- 明确提示：“合同「X」已创建，但报价单创建失败：{reason}。”；
- `{reason}` 直接取后端返回原文，不做前端改写。`createQuotation` 在这条链路上可达的失败原因是：型号不存在（产品被删除）、合同不存在（并发删除）、数据库异常；
- 保存已创建的 `contractId`；
- 后续操作不得重新创建客户或合同；
- 重试前查询数据库确认该合同尚无目标报价版本；
- 提供“重新创建报价单”；
- 提供“查看合同详情”；
- 重试时复用原报价行编辑态。

#### 7.6.2 文档生成失败

若合同和报价均成功而文档生成失败：

- 明确提示合同已创建；
- 提供“重新生成合同”；
- 提供“查看合同详情”；
- 重试前检查附件记录和文件是否已经存在；
- 重试不得重新创建合同或报价版本。

#### 7.6.3 客户或合同创建失败

- 停止后续步骤；
- 保留用户输入；
- 显示后端返回原因；
- 允许用户修正后重新提交。

- 没有改价时不写 `price_overrides` 键；
- `createQuotationVersionTx` 和下游事务函数新增参数必须可选；
- 存量迁移路径不传该参数，行为保持不变；
- 审计与新报价版本在同一事务落库。

## 9. 状态模型

建议前端将创建过程建模为：

```ts
type ContractCreateStage =
  | 'editing'
  | 'creating_account'
  | 'creating_contract'
  | 'creating_quotation'
  | 'generating_document'
  | 'partial_quotation_failed'
  | 'partial_document_failed'
  | 'complete'
```

关键状态：

- `accountId`：已有或本次新建客户 ID；
- `contractId`：合同创建成功后立即保存；
- `quotationId`：报价版本创建成功后保存；

任何阶段重试都必须从最后一个失败点继续，不得重新执行已成功的不可逆创建步骤。

## 10. 验收标准

条目按适用期次标注：`[P0]` 随 P0 独立发布验收，`[P1]`、`[P2]` 分别在对应期次验收（期次划分见 §12）。§15 为完整交付口径，只适用于全部期次交付后的整体发布。

### 10.1 抬头解析

除标注外全部为 `[P1]`。

- 正式编码前已收集 10–20 份真实样本（✅ 已完成 11 份，Gate 0 通过；六行式/四行式分布统计按本版输入口径豁免，见 §7.2.6 第 5 项）；
- 样本中的组合标签已单独统计，别名表有对应评审记录；
- 真实原文中包含 `税    号`、`帐号`、尾随空格时，六字段正确识别；
- 值内分段被规范化：税号、账号、电话值中的普通空格、Tab、全角空格全部去除；地址、开户行名的内部空格原样保留（§7.2.4 第 8 条）；
- 支持字段乱序、缺项、全角/半角冒号混用；
- 支持标签和值分两行；
- 地址中后续冒号不被截断；
- 值中的“号”字不影响匹配；
- 空文本和纯噪音返回空结果且不抛异常；
- “名称”正确识别为单位名称；
- “产品名称”不识别为单位名称；
- 重复字段只取第一个非空值；
- 组合标签能够被检出并提示手工拆分，系统不猜测写入；
- 组合标签命中时，地址、电话、开户行、账号四项均不被写入任何值；
- 仅命中组合标签、无字段命中时判定为失败，且提示同时包含未识别与待拆分说明；
- `parseBuyerHeader` 的返回结构能区分上述两种失败，不需要调用方自行判断。

### 10.2 客户边界

### 10.3 报价

### 10.4 部分失败

- `[P0]` 报价失败时明确说明合同已创建；

- `[P1]` 创建链完成后丢弃本地草稿，再次新建流程能正常创建第二份合同；

## 13. 风险与防范

| 风险 | 防范 |
|---|---|
| 解析错误导致合同抬头错误 | 确定性解析；不猜测；所有字段可改；成功提示要求核对 |
| 老客户名称被粘贴覆盖 | 已有客户和已有合同均禁止解析器修改 `account.name` |
| 客户 A 抬头污染新客户 | 切换客户模式时清空客户来源字段；验收列为 P0 |
| 改价失控 | 目录价与本次价并列；改价标记；同事务审计 |
| 报价失败后重复建合同 | 保存 `contractId` 改善交互；重试前以稳定请求标识查库并从失败点继续 |
| 重复点击造成重复记录 | 提交 loading 锁；阶段状态机防重入 |
| 刷新后前端状态丢失导致重复创建 | 使用稳定 `creation_request_id` 查库恢复；数据库为幂等权威依据 |
| 请求标识过早清除导致刷新后无法找回合同 | 标识写入合同后长期保留；“清除”只丢弃本地草稿；链未完成时按标识查库恢复 |
| 残留标识指向已完成合同被自动复用 | 按指向合同状态分流：链未完成则恢复，链已完成则丢弃草稿并重新生成标识 |
| 按标识查库缺少查询口，退化为时间窗口判断 | 新增按 `custom_fields` 的 `LIKE` 候选 + JSON 精确比对查询 IPC；查询限定当前微信账号业务库 |
| 空客户档案反复触发差异确认 | 档案五项全空直接写入；仅档案非空且存在差异时才确认 |
| 组合标签被当作未识别行静默跳过 | 组合标签登记为独立别名类别，命中后进入待拆分提示 |
| 前端改价标签与后端审计不一致 | 前后端统一调用 `shared/isPriceOverride` |
| 组合标签被错误拆分 | 第一期只识别并提示手工拆分；样本验证前不启用启发式 |
| 真实客户资料泄露到仓库 | 原始样本仅本地保存；fixture 脱敏后才允许提交 |
| 文件已移动后按钮无反应 | 主进程检查文件存在性并返回结构化错误 |
| 迁移路径因签名变化失败 | 新增审计参数全部可选；迁移路径回归 |
| 页面因产品过多变得很长 | 搜索优先、限制候选数量；第二期右侧工作区独立滚动 |

## 15. 发布门槛

10. TypeScript 检查无本次新增错误；
11. `docs/HANDOVER.md` 同步完成；
