## 1. 产品定位

- **用户可见名称**：年度经营复盘。
- 原「微信年度回忆」式年度报告（`/annual-report` 链路，含双人报告）**不再作为产品方向**：入口已在 `src/components/Sidebar.tsx:423-431` 以 `{false && …}` 隐藏（注释「年度报告 - PRD v2 隐藏」），双人报告无独立入口且其唯一入口在已隐藏的 AnnualReportPage 内。本规格不删除这些代码（清理属最后阶段，见 §11），也不复用其页面。
- 与周复盘的分工：
  - **周复盘**（现有 `salesReportService.generateWeeklyReview`）回答「下周做什么」——本周热了/变冷/建议放弃。
  - **年度经营复盘**回答「过去一年为什么赢、为什么输、下一年度资源投向哪里」——经营结果、漏斗、客户结构、沟通投入、分配公平性。
- **第一版只做确定性数据统计**。AI 诊断与下一年度行动计划是后续阶段（§9）；第一版页面不出现任何 AI 文案区块。
- 双人年度报告继续隐藏；旧个人社交年度报告代码的清理属于最后阶段。

- 消息行关键字段（原生层直出）：`create_time`（**秒**，chatService.ts:5473）、`local_type`、`computed_is_send ?? is_send`（本人发送主口径）、`real_sender_id`/`sender_username`（群聊经 Name2Id）。消息按会话分表 `Chat_<hash>`。

## 3. 时间、as-of 与金额口径（全局裁决）

### 3.0 时间契约（统一规则，适用一切指标与时点型展示）

每个报告由 IPC 顶层返回**一个范围类型字段 `scopeKind` 和四个时间字段 `periodStart / periodEndExclusive / asOf / generatedAt`**（见 §7.2）。

| 情形 | scopeKind | periodStart | periodEndExclusive | asOf | 实际统计区间 |
|---|---|---|---|---|---|
| **当前年度**（`year = 本地当前年`） | `current_year` | 当年 1 月 1 日 00:00.000 | 下一年 1 月 1 日 00:00.000（名义自然年边界） | `generatedAt` | `[periodStart, asOf)`（自然年末尚未到达，绝不用 `periodEndExclusive` 截断现实） |
| **已结束的历史年度** | `historical_year` | 当年 1 月 1 日 00:00.000 | 下一年 1 月 1 日 00:00.000 | **= `periodEndExclusive`** | `[periodStart, periodEndExclusive)` |
| **历史以来**（`year=0`） | `all_time` | `null` | `null` | `generatedAt` | 下界 = 各数据源可用最早时间（含），上界 = asOf（不含） |

- **`generatedAt` 永远只表示报告实际生成时间**，不兼作任何历史报告的数据时点（历史年度的数据时点是 `periodEndExclusive`，不随生成时间变化；但**时间边界稳定 ≠ 底层数据不可变**——迟到同步、补录核销、迁移、删除、修复都可能改变历史年度统计结果，缓存与失效策略见 §7.2）。
- **当前快照 / 历史年末重建 / unavailable 的区分不在顶层概括**：同一份历史报告中会同时存在按事件时间直接可算的指标、重建成功的指标、重建失败而 unavailable 的指标——该区分由**每个指标/区块的 `coverage.status` 与 kind 字段**表达（如 `funnel.snapshot.kind`），顶层不设统一 `asOfKind`。
- 当前投影（`customer_profile.stage`、`opportunity.stage/status`、`last_contact_at`）只在 `scopeKind='current_year'/'all_time'` 时可作为时点事实；`historical_year` 下只有事件流重放（append-only：`intent_tag_log`、`opportunity_event`、`contract_status_history`、`audit_event`）是合法事实源，重放目标时点 = `periodEndExclusive`。
- 禁止用词：「历史年度的年末快照」（当前投影冒充）；当前年度的任何比较使用 `yearEnd`（自然年末尚未到达）。

### 3.1 年度范围与时区

- 时区 = 运行设备**本地时区**（与 `getWeekRange/getMonthRange` 先例一致）。
- `periodStart` / `periodEndExclusive` = 名义自然年边界（§3.0 表），左闭右开，毫秒比较；**历史以来（all_time）两者为 `null`**，下界取各数据源最早可用时间。
- 事件类指标的统计区间（下文卡片简写「年度区间」）**统一为左闭右开**，SQL/伪代码一律写作 `timestamp >= start AND timestamp < endExclusive`：当前年度 = `[periodStart, asOf)`；历史年度 = `[periodStart, periodEndExclusive)`；历史以来 = `[最早可用时间, asOf)`。WCDB 秒值统一 `×1000`（禁止跨单位直接比较，P0-2A.1 bug2 先例）。
- **边界归属**：恰好发生在下一年 1 月 1 日 00:00:00.000 的事实只属于下一年度，**不得同时计入两个年度**；`asOf` / `periodEndExclusive` 时刻本身发生的事件不计入本报告（右边界开区间）。

### 3.2 时间字段裁决（修订）

| 指标域 | 时间字段 | 单位 | 修订说明 |
|---|---|---|---|
| 客户创建 | `account.created_at` | ms | 不变 |
| 阶段事件 | `intent_tag_log.created_at` / `opportunity_event.created_at` | ms | 不变 |
| 合同签约 | **仅 `contract.sign_date`** | ms | **统一口径：签约数/金额只按 sign_date；sign_date 为空的合同不计入任何年度签约指标；不得用 created_at 冒充签约时间**。若存在 `status IN ('signed','shipped')` 且 `sign_date` 为空的遗留记录 → 指标记 `partial`，warnings 返回缺失数量（记录本身不进入指标）。全文已删除一切「回退 created_at」表述 |
| 核销 | `allocation.reconciled_at`（legacy_confirmed 回退 `confirmed_at` 并降级） | ms | 不变 |
| 出货 | `contract_status_history.created_at`（to_status='shipped' 首次） | ms | 不变 |
| 消息 | WCDB `create_time` | s×1000 | 不变 |
| **分配发生** | **`audit_event.created_at`（action IN ('lead_assign','lead_transfer')）** | ms | **修订：`assignment.updated_at` 被认领/回收/移交/SLA 提醒四类操作改写（§2.3），不得作为分配时间；`version=1` 也不足以识别（认领后 +1）。移交新归属的事实源是 `lead_transfer` 审计（detail.toSales/assignmentId），不是 `lead_assign`。** |
| 分配落库（辅助） | `assignment.updated_at` + `assignment.source` | ms | 只用于辅助说明（source 区分本机/同步来源、当前在途行状态），**不作为历史事实，也不用于计算审计覆盖率**（可变当前行 ≠ append-only 事件总体，见 E1 缺口检测口径） |
| 客户最近联系 | 当前年度：新增聚合优先，回退 `last_contact_at`(s×1000) 须标 partial；历史年度：`MAX(WCDB create_time) WHERE create_time < asOf`（**需新增只读聚合能力，V1 不具备 → 历史年度相关名单 unavailable**） | — | 修订，见 §3.0/§10 |

**联系时间裁决明细**：现有 `getAnnualReportStats` 无按会话最后消息时间输出（daily 为全局合并），`last_contact_at` 只回填当下。因此：
- **当前年度**：B6/C6/C7/C8/D7 可用 `customer_profile.last_contact_at`（或 account 同名列）近似「截至生成时间的最近联系」，**必须标 `partial`** 并固定警告「部分客户最后联系时间以详情打开时回填为准」；
- **历史年度**：不得使用当前 `last_contact_at`。在新增 per-session as-of 聚合（只读，`MAX(create_time) WHERE create_time < asOf`，限定 CRM 客户会话）落地前，历史年度的这五类名单一律 `unavailable`（移出 V1，§10）。

### 3.3 金额

单位人民币元（`contract.amount`、`allocation.credited_amount`、`payment_record.amount_net` 均 REAL 元）。计算层不预先舍入，展示层两位小数、≥1 万元显示 `¥x.x万`。`amount_hint`（认领提示额）不得当合同金额。

### 3.4 撤销/删除/冲正/legacy

- 物理删除（+activity_log 墓碑）后对象不可见，且**历史年度计数不可重现**——由完整性模型表达，不做墓碑回放。
- `allocation` 撤销（undoAllocation 回 pending）自然退出核销口径；`invoice voided`、`logistics cancelled` 按当前状态排除。
- `legacy_confirmed` 计入回款（与 creditedTotal 一致），回退时间规则见 §3.2。
- 跨微信号分库/legacy 库文件不合并统计。

### 3.5 「历史以来」

保留 `year=0`，asOf = generatedAt，语义 = 本地当前账号库全部数据；UI 显示「历史以来」；不与单年混轴。

## 4. 数据完整性模型（修订）

四态枚举由主进程计算并随 IPC 返回，UI 只渲染不推断。判定**不依赖「表是否存在」**（Schema 初始化即建业务表，表存在≠模块使用过）：

| 状态 | 判定规则 | UI 文案 |
|---|---|---|
| `empty-zero` | 查询成功、数据源已连接，但年度内**没有符合条件的事实**（真实零） | 显示 0 / 空列表，附口径说明 |
| `partial` | 数据存在但受限：使用了回退字段（legacy 回退时间、当前年度 last_contact_at 近似）、事件流覆盖率不足、`sign_date` 缺失的已签约遗留记录、同步积压（backlog>0 且最近同步超 24h）、审计流未覆盖 sync 导入行 | 黄点「数据部分完整：{reasonCodes 文案}」，tooltip 列明细 |
| `snapshot_only` | 该指标只有时点投影形态且该形态**对所选年份合法**（仅当前年度的历史无关展示，如商机当前分布辅助视图）；或事件流重建后仅能给出分布级（非比率）结果 | 标注「当前快照（截至生成时间）」/「历史年末重建（覆盖率 x%）」 |
| `unavailable` | 查询失败、WCDB 未连接、**当前版本不支持所需历史查询**（如历史年度 per-session 联系时间聚合）、无访问范围、**当前投影无法重建历史时点** | 「暂无可靠数据」，**禁止显示 0 冒充真实零**，区块折叠 |

- **当前投影 ≠ 历史时点**：历史年度指标若唯一数据源是当下投影（无事件流可重放），一律 `unavailable`，不因表里有行而显示任何值。
- coverage 结构化字段进入接口（§7.2）：`{ source, status, coverageFrom, coverageTo, rows, reasonCodes[] }`，可选 `exactCoverage?: boolean` 与 `coverageRatio?: number|null`——**仅当分母与分子来自同一可数总体时才允许返回 ratio**（如 B1/B3 的事件流覆盖：有事件会话/绑定会话）；审计覆盖类（E1 对中枢下发事实）**分母不可知，`coverageRatio` 必须为 `null` 且 `exactCoverage=false`**。UI 依据字段渲染，不根据当前时间或字段缺失自行推断。
- 判定责任：全部在主进程统计模块内，按指标逐个给出。

**总裁决（修订）**：本区块 V1 只呈现「本机审计记录视角下的实际分配事实与贡献」；**批次成功率、计划份额、份额偏差全部移出 V1**（事实源缺口见 §2.3，幸存者偏差不可接受）；不得出现「计划偏差」「公平性结论」类文案。

**E1 分配事实 assigned_facts**（初始分配与移交分开统计，不得相加后称「新增分配线索数」）
| 项 | 口径 |
|---|---|

| 排除条件 | 同一 assignmentId 的后续状态变化不改写审计（append-only 天然幂等）；`transfer_remove`/`recycle` 类 sync 事件不属于归属落定事实 |
| sync 缺口检测（只做检测，不算百分比） | 目标区间内存在 `audit_event(action='sync_apply') AND detail.type IN ('assign','transfer')`（lanSyncService.ts:697-760，中枢下发 LAN/Central 均落地为此形态）→ 说明审计流未覆盖中枢下发事实。此时 E1 `coverage.status='partial'`、`reasonCodes` 含 `sync_import_not_audited`、**`coverageRatio=null`、`exactCoverage=false`**，固定文案「检测到中枢下发的分配/移交记录；当前统计只覆盖本机审计事件，实际总量可能更高」；**禁止显示「覆盖率 x%」**。区间内未检测到 sync_apply → 只能称「本机操作审计完整」，**不得宣称跨设备或中央全量完整** |
| 空数据语义 | 无本机 lead_assign/lead_transfer **且**无区间内 sync_apply → `empty-zero`（含义=「本机审计中无分配事实」）；无本机审计但存在 sync_apply → **不得显示真实零**，返回 `partial`（缺口状态）+ `sync_import_not_audited` 警告；查询失败 → `unavailable` |
| 是否 V1 | 是（拆分计数 + 缺口检测） |
| 可信度 | 本机操作事实 A；存在 sync_apply 时整体 partial；**不宣称全量 A 级** |

**E2 批次成功率 batch_success_rate**：**移出 V1**。`lead_assign_batch` 仅 `assigned>0` 落行，全部失败批次无审计，`Σassigned/Σcount` 无法计算真实值（幸存者偏差）；不得以「有成功结果的已记录批次统计」名义变相进入 V1。→ §10「需要新增审计行为后才能做」。

**E3 有效跟进客户数 effective_followup**：`assignment.claimed_at ∈ [start, asOf)`（claimed_at 为认领动作一次性写入、历史可靠）且对应 `lead.first_contacted_at` 非空；V1 是；B。

**E4 合同贡献 contract_contribution**：按 A4 同款 sign_date 口径的合同，经 `contract.account_id → account.owner_sales` 当下值分组求和；owner_sales 会被离职移交改写 → 历史归属不可重现，**恒标 partial**（reasonCode=`owner_current_value`，文案「按当前归属销售统计」）；V1 是；B。

**E5 已核销回款贡献 credited_contribution**：A6 口径按 `allocation.sales_name`（认领销售，认领动作事实）分组为主口径；`owner_sales` 口径为辅且同 E4 降级；V1 是；A/B。

**E6 轮询计划份额 planned_share**：**移出 V1**。批次审计缺 plannedPerSales、销售顺序、起止游标、权重/负载快照，且 round_robin 为成功驱动状态机（计划即实际轨迹，无先验份额）；`buildDistribution` 输入不可历史重建。→ §10。

**E7 份额偏差 share_deviation**：**移出 V1**（依赖 E6）。现有数据最多展示：初始分配与移交分项事实（E1）、幸存批次 detail 中的实际 `perSales`、sync 缺口检测状态；**不得称「计划偏差」或「公平性结论」，不得显示任何覆盖率百分比**。

**E8 失败与降级解释（数据说明区固定文案）**：保留三句——全部失败批次不留批次审计（assigned=0 不落行）；部分失败的 skipped 只在幸存批次的 audit detail 中；round_robin 游标写盘失败为辅助降级（≤一批份额漂移、长期自愈，weight/load 不读写游标）。依据 crmAssignmentService.ts:953-998。

- **缓存策略（V1，账号作用域）**：
  - **类型**：仅主进程**内存缓存**；不做跨进程、跨应用重启的持久缓存；不把报告写入普通 config；**不跨账号/业务库复用**（应用支持运行时切换微信账号并重开对应 salesDb/crmDb，按 year 缓存会让另一账号命中错误报告）。
  - **键**：`{ accountScopeId, year, reportSchemaVersion }`。`accountScopeId` 由主进程根据当前规范化微信账号与实际业务库身份生成（S3 修订：完整复合键，如长度前缀/JSON 编码——不使用短哈希折叠，无碰撞面；实际业务库身份核对 `salesDbService.currentDbPath()` / `crmDbService.currentDbPath()` 等真实入口，不得只按 config wxid 推导假定文件名），必须能区分不同 wxid 与不同 salesDb/crmDb；该内部键不写日志、不向渲染层暴露（原始数据库路径同样不暴露）；**解密密钥、Token 及其他秘密不得进入缓存键或日志**。
  - **TTL 与重算**：所有 scopeKind 统一短 TTL（建议 10 分钟）；`generate` 默认强制重新统计并覆盖同作用域缓存；`getReport` 只读取「当前账号作用域」的未过期缓存，过期或不存在时返回明确的 cache miss/stale 结果，**绝不回退其他账号或其他业务库的报告**；同一 `accountScopeId + year` 已有生成任务运行时合并等待，不重复生成。
  - **强制失效条件（至少）**：① 当前微信账号切换；② salesDb/crmDb reopen；③ WCDB 重新连接或切换账号；④ CRM 客户、合同、核销、出货、阶段、Assignment 数据发生写入；⑤ LAN/Central sync 成功应用业务事件；⑥ 手动排除名单或内部人员名单变化；⑦ 报告 Schema/指标版本升级。实现阶段尽量复用既有失效事件；没有统一失效总线的领域，V1 依靠短 TTL + generate 强制重算保证正确性，**不得宣称缓存实时一致**。
  - **历史年度缓存语义**：历史年度的时间边界恒定（`asOf = periodEndExclusive`），但底层事实仍可能因迟到同步、补录核销、迁移、删除、修复而变化——因此历史年度同样使用账号作用域缓存、同样受 TTL 与失效规则约束；**「边界稳定」不等于「底层数据不可变」**。
  - **`annualReview:getAvailableYears` 同样按账号作用域隔离**：其缓存与运行中任务必须使用相同 `accountScopeId`，不得只按 year 或全局单例返回其他账号的年份。
  - UI 不依据本地时间判断缓存新鲜度，一切以返回字段为准。

- 历史无法重建的指标：该字段整体缺省 + `coverage[key].status='unavailable'` + `reasonCodes` 含 `history_not_reconstructable`；UI 依据这两个事实渲染，不做本地推断。
- 不设计第二套阶段/金额/客户身份模型：阶段输出用 canonical stage + `FUNNEL_BUCKET`；金额一律元；客户身份只引用 `account.id/customer_id`。
- IPC 命名：**新增 `annualReview:*`；保留现有 `annualReport:*` 原样不动**（旧页面隐藏但可运行，避免破坏隐藏功能；改名迁移并入最后清理阶段，§11）。

## 8. AI 诊断与下一年度行动计划（S7；本章为已实现的输出契约）

实现位置（S7.1，本轮不含 UI）：

| 模块 | 路径 | 边界 |
|---|---|---|
| 纯模块 | `electron/services/annualReviewAiCore.ts` | 输入投影 / prompt / 输出解析校验；零 Electron、零 IO、零时钟、不改入参 |
| 调用接口 | `electron/services/annualReviewAiService.ts` | 报告校验 → 配置 → 投影 → 模型调用 → 解析；唯一模型出口经参数注入 |

总原则（原文保留；仅第 4 条按 V1 收敛）：

- AI 只接收 `AnnualReviewReport` 聚合指标与结构化经营事实（同 `salesReportService` 纪律：只喂聚合，不喂聊天正文；第一版不发送任何原始聊天正文）。
- AI 不负责计算金额、排名、转化率；其输出数字必须能在 report 字段中找到对应。
- AI 只做：解释确定性结果（为什么赢/输假设）、生成下一年度资源投向建议。
- 每条建议绑定 `metricKey`；无证据不展示。**V1 收敛为只绑 `metricKeys`**：原文「或 `evidence_key`（shared/evidenceKey.ts 规范）」在 V1 不适用——V1 不把消息交给 AI，无法产生可回查的 messageKey，`evidence_key` 类证据留待后续版本。
- AI 不可用/未配置时确定性报告完整可用（与周复盘「未配置即失败」相反，AI 层整体可选）。

输入是报告的**投影**而非删减：只有下列六类，逐字段显式取自报告，键名与取值均可回溯到报告字段。

| 输入键 | 内容 | 来源 |
|---|---|---|
| `meta` | `year / scopeKind / asOfDate / generatedAtDate / dataRange / timezoneNote / completeness` | 报告同名字段（时间为本地 `YYYY-MM-DD` 视图，不改变报告时间语义） |
| `metrics` | 标量聚合指标 `{key, value, state}`：`summary.*` 10 项 + `funnel.stuck` + `communication.volume/contacted/outboundRate` + `salesAssignment.effectiveFollowup` | 报告 `value/state`（`funnel.stuck`、`salesAssignment.*` 的 state 取 `coverage.status`） |
| `distributions` | `funnel.customerStage/opportunityStage/stageFlow/lostBreakdown` 的 `{kind, state, buckets}`（`kind` 与桶名均经固定枚举白名单） | 报告 `funnel.*.distribution` / `lostBreakdown.customerPreviousStage` |
| `series` | `monthly.contractSign / monthly.credited / monthly.messageVolume` 的 `{state, points:[{month,value}]}` | 报告 `monthly.*`（`value` 分别取 `amount` / `amount` / `count`） |
| `coverage` | 每个 metricKey 的 `{status, source, rows?, exactCoverage?, coverageRatio?, reasonCodes?}`，键集合 = 报告 coverage 键集合（升序） | 报告 `coverage`（`source`/`reasonCodes` 必须在白名单内，否则整份报告被拒，见 §8.1.1） |
| `warnings` | `{code, metricKeys, counts?}`——**不含 `message`** | 报告 `warnings`（`code` 必须在白名单内，否则整份报告被拒，见 §8.1.1） |

**明确不进入输入**（第一版）：客户明细列表（C1–C8 行）、客户姓名、`account.id`/`customer_id`、`sessionId`/`wxid`、D7 长期未联系名单、E 组 per-sales 明细（`contractContribution`/`creditedContribution`/分配分组）、`opportunityReasons` 自由文本、`sourceSummary`（表名与行数）、数据库路径、SQL、Token/密钥、聊天正文。

#### 8.1.1 字符串白名单与 AI 输入契约（fail closed）

报告 validator 对 `coverage.source`、`coverage.reasonCodes[]`、`warnings[].code`、分布 `bucket` / `kind` **只校验「是非空字符串」**，不校验取值——这些字段若来自被污染的报告，就能把客户姓名、`sessionId`/`wxid`、数据库路径、SQL、Token、聊天正文或提示注入文本直接送进 prompt。因此 AI 侧独立做一层**契约校验**：

`validateAnnualReviewAiInputContract(report)`（纯函数、不抛异常）在**模型调用之前**逐项检查上表五个字段是否命中白名单：

| 字段 | 白名单 |
|---|---|
| `coverage[].source` | `ANNUAL_REVIEW_AI_ALLOWED_SOURCES`（报告 pipeline 实际产出的 source 全集，含 `derived:contract_amount/dealing_customers` 与 `local_facts`） |
| `coverage[].reasonCodes[]` | `ANNUAL_REVIEW_AI_ALLOWED_CODES`（统计层全部 warning/reason code 字面量，45 条） |
| `warnings[].code` | 同上（同一白名单） |
| 分布 `buckets[].bucket` | `FUNNEL_ORDER`（shared/salesStage，阶段口径唯一源，不复制副本） |
| 分布 `kind` | `current_snapshot` / `historical_reconstruction` |

**任一项未命中 → 整份报告不生成 AI 分析（fail closed），不调用模型、不静默删除/替换/降级任何值**，返回 `unsupported_report_contract`（§8.3）。理由：把含未知契约值的报告「美化」后继续交给模型，会把数据质量缺口藏在一份看起来正常的诊断背后；宁可整份不做，也不产出建立在未知语义上的结论。

- 投影函数 `buildAnnualReviewAiInput` **返回结构化结果**（`{ok:true,input}` / `{ok:false,violation}`），不再承担「过滤脏值后继续运行」的职责；service 先校验再构造，builder 自身的契约检查是防御分支。
- 违规对象只含**字段名与位置**（`AnnualReviewAiContractViolation{field, metricKey?}`），不携带违规值本身；返回给调用方的 `message` 是固定常量，绝不拼接未知字符串、报告内容、异常正文或路径。
- 确定性报告本身不受影响：该报告仍可正常查看与导出（`validateAnnualReviewReport` 不因此收紧）。

`warnings.message`（以及一切人类可读文案）不再发送：AI 只需知道「哪个指标有哪类缺口」，含义由稳定 `code` 决定；文案是自由文本，正是各类敏感内容的潜在载体。

其余字符串字段（`scopeKind`、`timezoneNote`、`state`/`status`、月度 `month` 键、`metricKey`）在报告契约里已是封闭枚举或严格格式，并由 `validateAnnualReviewReport` 强制校验，不作为自由文本处理。

测试用双向守门 + 行为断言：`输入里的每个取值必须命中白名单` + `统计层源码里的每个 code/source 字面量必须已被白名单收录`（白名单多余条目同样失败），以及**五类污染各自单独构造报告**并断言失败码 / 模型零调用 / 文案无探针 / 原报告未被修改。

其他确定性规则：

- `unavailable` 指标的 `value` 必为 `null`（不是 `0`）；不可得的月度序列 `points` 必为 `null`（不是空数组）。
- `monthly.messageVolume` 与 `communication.monthlyTrend` 是同一份 D5 结果，只发送一条，避免同一序列在 prompt 里出现两次。
- 同一报告两次投影深等，`buildAnnualReviewAiPrompt` 无时钟/随机/环境读取 → 同输入必得同一 prompt。

### 8.2 AI 输出契约（严格 JSON）

```jsonc
{
  "executiveSummary": "string",
  "diagnoses": [{ "title": "string", "observation": "string", "hypothesis": "string", "metricKeys": ["summary.contractAmount"], "confidence": "high|medium|low" }],
  "actions":   [{ "priority": 1, "action": "string", "rationale": "string", "metricKeys": ["summary.creditedAmount"], "horizon": "next_quarter|next_half|next_year" }],
  "risks":     [{ "risk": "string", "metricKeys": ["communication.volume"] }]
}
```

- `priority`：整数 `1|2|3`（1 最高）；不接受字符串 `"1"`、`"P1"`、`0`、`4`、小数。
- 长度上限：`executiveSummary` ≤ 800 字；`title` ≤ 60 字；其余文本字段 ≤ 240 字。
- 条目上限：`diagnoses` ≤ 6、`actions` ≤ 8、`risks` ≤ 5；每项 `metricKeys` 1–6 个。
- 三个数组允许为空（没有把握宁可不写），但**顶层四个键必须全部存在，且不得有额外键**。
- 校验口径 = 严格拒绝，不做修补：空输出、非 JSON、非对象、缺字段、额外字段、数组超量、空文本、超长文本、非法枚举、**未知 metricKey**、重复 metricKey 一律整体失败（不部分采信、不截断、不填默认值）。文本字段与 metricKey 两端空白会被 trim 归一。
- `metricKeys` 必须存在于报告 `coverage` 键集合中（键集合即白名单，由数据决定，不靠提示词自觉）；`metricKeys` 非空 → 每条判断/行动/风险都带真实证据锚点。

#### 8.2.1 数字声明识别（V1：正文不得给出具体数值）

合法 `metricKeys` **不能**证明正文里的数字真实：`回款比签约高 83%`、`损失 100 万元`、`排名第一` 都可以挂着合法 metricKey 出现，而报告里根本没有这些数。因此全部文本字段机械识别数值声明，命中即整体失败；确定性数字由页面依据 `metricKeys` 从原报告渲染。

**校验范围**：`executiveSummary`、`diagnoses[].title/observation/hypothesis`、`actions[].action/rationale`、`risks[].risk`。

**识别规则**（`ANNUAL_REVIEW_AI_NUMERIC_RULES`，可解释规则表，命中任一即判违规）：

| id | 规则 | 示例 |
|---|---|---|
| `decimal_digit` | 任意 Unicode 十进制数字（含全角） | `83%`、`８３％`、`2026` |
| `cn_ordinal` | `第` + 数字字符（中文序数） | `排名第一`、`第二阶段`、`第三季度` |
| `cn_ranking` | `前` + 数字字符（中文排名） | `前五`、`前十`、`前三名`、`排名前三`、`位列前五` |
| `cn_fraction` | `百分之`/`千分之`/`万分之` + 数字 | `百分之五`、`百分之十五`、`千分之五`、`万分之三` |
| `cn_ratio` | 数字字符 + `成`/`折`/`倍`（中文比例/倍数） | `增长八成`、`三倍`、`三成以上` |
| `cn_quantity` | 数字字符 + 量词（金额/数量/时间/等级；`分`/`角` 需后接「钱」） | `回款三万元`、`十二个客户`、`三个月`、`二零二六年`、`一千万`、`三级客户`、`一分钱` |
| `cn_numeral_run` | 连续 ≥2 个数字字符 | `二零二六`、`十二个`、裸 `千万`（金额千万） |

**普通词汇不受限制**：单个数字字符后既不接量词、也不构成连续串时不算数值声明，因此 `统一口径`、`保持一致`、`两类风险`、`十分谨慎`、`万一发生`、`一方面需要关注`、`两端协同不足`、`一一核实`、`一成不变`、`前期跟进`、`前置条件`、`提前准备` 全部放行。

**豁免是「按匹配位置」而不是「全局字符串遮盖」**（`ANNUAL_REVIEW_AI_NUMERIC_EXEMPTIONS`，每条带 id / 类型 / 理由，测试断言每条都在起作用）：

| id | 类型 | 放行条件 | 为什么不可能表示数量 |
|---|---|---|---|
| `qianwan_adverb` | 上下文锚定 | `千万` **后接副词后缀**（要 / 不能 / 别 / 避免 / 务必 / 不可 / 注意 / 记得 / 不要 / 谨记 / 谨防 / 防止 / 保持 / 把握） | 该组合是「务必」义 |
| `wanyi_conjunction` | 非数量形式 | `万一` | 中文数量写作「一万」，「万一」不是数量形式 |
| `yiyi_sequential` | 非数量形式 | `一一` | 表示逐个（一一核实），数量写作「一万一千」这类 |
| `wanwan_archaic` | 非数量形式 | `万万` | 副词或古旧量词，现代中文数量写作「亿」 |
| `yicheng_idiom` | 非数量形式 | `一成不变` | 成语；**单独出现的 `一成`＝10% 仍被 `cn_ratio` 拒绝** |

关键区别：**裸 `千万` 是真实金额，绝不放行**。`合同金额千万`、`回款千万`、`达到千万`、`超过千万`、`千万级规模`、`一千万` 全部判违规；只有 `千万 + 副词后缀` 才豁免。同一句里两种用法并存时按位置分别判定——`千万不要忽略回款千万的风险` 整体仍判违规。豁免对片段做等长占位替换，不会把相邻字符拼成新的数值串。

**已知歧义**（机械匹配，不是自然语言语义理解）：

- `第一时间` 会被 `cn_ordinal` 拒绝（与「排名第一」共用「第一」）——这是为保住序数识别而接受的误杀，未做豁免；
- 数字 + `级`/`档` 判为数值（`三级客户` 正确拒绝），代价是「两级分化」这类含数字语素的成语也会被拒绝（保守方向选「宁可拒绝」）；
- `分`/`角` 只在后接 `钱` 时算量词：`一分钱` 拒绝、`十分谨慎` 放行；`一角钱` 拒绝、`一角（角落）` 这类不同写法不在识别范围；
- `一处`/`一方面`/`一类` 这类「数字字符 + 非量词」的模糊表述按普通词汇放行（`一处` 表示「有一处缺口」，非具体数量）；
- `前年`/`前期` 等不以数字字符结尾的「前 X」不受 `cn_ranking` 影响（`前三年` 会被拒绝）；
- 规则/豁免变更必须同时改规则表、豁免表、system prompt 与本表，并补对应测试。

**其余口径**：违规 → 整体失败，失败码 `numeric_claim`（文案只报字段路径与命中的规则 id，不回显模型原文）；唯二不受影响的位置是 JSON 字段 `priority` 的取值与 `metricKeys` 键名（都不是文本字段）。

### 8.3 调用与失败契约

- 复用现有 AI 基础设施，**不新增依赖、不建第二套客户端**：出口固定 `simpleCompletion → callChatCompletion`，因此日调用上限闸门（HTTP 之前阻断并记 `blocked` 账本行）与用量账本自动生效。
- 参数：`temperature=0.2`、`response_format={type:'json_object'}`、`max_tokens=2400`、`timeoutMs=60000`、关闭思考模式。
- 账本：`purpose='annual_review_ai'`（稳定值，改动等于账本口径变更）、`trigger='annual_review'`、`promptVersion='annual_review_ai_v1'`。
- 失败一律返回结构化状态码，**不伪造诊断**：

| code | 含义 | 返回文案 |
|---|---|---|
| `invalid_report` | 报告未通过 `validateAnnualReviewReport`（校验在调用**之前**，不为脏数据付费） | 固定文案（不含校验细节；需定位问题由调用方自行调用 validator） |
| `unsupported_report_contract` | 报告通过了确定性校验，但含 AI 投影白名单外的枚举取值（§8.1.1）——**在模型调用之前判定**（与 `invalid_report` 的区别：报告本身合法可用，只是 AI 层不支持该契约取值） | 固定文案（不含未知值；需定位问题由调用方自行调用 `validateAnnualReviewAiInputContract`） |
| `not_configured` | AI 未配置（缺 API 地址或密钥） | 固定文案 |
| `budget_blocked` | 触发日调用上限（与模型故障区分） | 固定文案 |
| `call_failed` | 调用异常：超时 / 取消 / 其他网络或模型故障 | 各一种固定文案（超时、取消、其他） |
| `empty_output` | 空输出（含围栏内为空） | — |
| `invalid_json` | 输出不是合法 JSON | — |
| `invalid_shape` | 结构/枚举/长度/metricKey 不合约 | — |
| `numeric_claim` | 文本字段含数字声明（§8.2.1），文案只报字段路径与命中规则 id | — |

- **错误脱敏（强制）**：调用失败的返回文案是**编译期常量**，不是异常的投影。底层 `error.message` 常携带 API URL、密钥、供应商响应正文、数据库路径与堆栈，一旦透传就会随错误提示、日志、崩溃报告扩散；因此 `AnnualReviewAiService` 只对异常做**分类判断**（额度阻断用结构化判定 `isBudgetBlockedError`、取消用 `AbortSignal` 状态、超时对异常文案做正则归类），分类用的原始文案**绝不外泄**，失败结果也只有 `{ok:false, code, message}` 三个键。本轮不新增日志。
- **判定顺序**（全部在模型调用之前或之后有序收敛）：报告结构校验 → AI 输入契约校验（fail closed）→ AI 配置 → 投影与 prompt → 模型调用（额度闸门在 HTTP 之前）→ 输出解析。契约不合约时既不构造也不发送 prompt。
- 失败与成功路径均**不改动**确定性报告：AI 层不写缓存、不持久化、不修改入参，报告读取与导出不受影响；`unsupported_report_contract` 的报告仍可正常查看与导出。
- 窄依赖注入：唯一模型出口经 `AnnualReviewAiRunOptions.completion` 注入；测试注入后本模块不接触 `aiApiClient`，不发真实请求。
- 尚未完成（S7.2+）：IPC（`annualReview:aiAnalysis` 类）、preload、页面区块、结果持久化；页面需按 §8.2.1 从原报告渲染确定性数字，AI 文案只做定性解释。
