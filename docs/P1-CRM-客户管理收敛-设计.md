### 缺口清单

1. **客户覆盖率**：建档仅 218 人 ≪ ~2,837 好友。由 P0-5 分类引擎补入口（第三刀落库），不在本设计范围内。
2. **成交识别无「AI 报候选 → 人工拍板」闭环**：AI 判定直接进漏斗口径，缺销售确认环节。
3. **页面职责重叠**：客户页「值得跟进」视图与今日行动同源同闭环（详见 §二），三层重复砍成一层。

⚠️ 数据口径警示：weflow-crm.db 的 lead 表（875 条）内容经用户确认为**测试数据样本**，非真实留资线索；
一切以 lead 表为输入的业务结论（如「加微漏损」）均不成立。真实业务数据入池后相关指标须重跑。

## 二、已拍板：客户页职责切分（方案 A，用户 2026-08-27 定案）

```
首页·今日行动 = 执行入口。"今天要做什么"——动作卡流 + 待办侧栏
/customers    = 查询与管理入口。"我的客户都在什么状态"
               保留：「全部客户」（阶段筛选/搜索/360 档案）、「AI 新发现」、「待确认」队列（新增，见 §三）
               删除：「值得跟进」视图（与今日行动同源同闭环的重复品）
```

### 2.1 决策依据（用户拍板理由记录）

1. 「值得跟进」比重复还多余——「全部客户」本身就有「有信号置顶」能力，客户页内部此前已是两个视图做同一件事
   （按优先级看有信号的客户）。删后信号置顶 + 阶段筛选覆盖其 90% 用途，剩余 10%（priorityScore 精确排序）
   就是今日行动本体。
2. 页面关系从互相稀释变为互相导流：管理时看到信号 → 点一下去执行入口处理。

### 2.2 必做的「桥」（删除的同时新增）

「全部客户」列表中有信号的客户行加徽章/标识，点击跳转到今日行动对应卡（或展开 360 看信号详情）。
只做徽章 + 深链，不保留任何形式的第二行动列表。

### 2.3 深链兼容性前置检查（2026-08-27 代码核实）

| 深链参数 | 现落点（CustomerWorkspacePage.tsx:73-96） | 删除 follow 后影响 |
|---|---|---|
| `?stage=`（漏斗下钻） | 已显式 `setTab('all')` | 无影响 |
| `?id=`（灵感信箱）/ `?sid=`（行动卡） | `openCustomer()` 直开 360，不依赖视图 | 无影响 |
| 默认视图 | `useState<ViewTab>('follow')`（:44） | **唯一改动点**：ViewTab 移除 `'follow'`，默认切 `'all'` |

## 三、合并刀范围（09-01 复盘会后执行，单刀三件事）

> 三件事必须同一刀收口的原因：删视图后今日行动成为唯一行动入口，第 2 刀批量建档会让所有新客户的
> AI 卡涌向这一个池子——不做节流，前两件越成功，今日行动越早被打爆（用户指出：这是成功本身的风险）。

### 刀件 1：删「值得跟进」视图

- ViewTab 类型移除 `'follow'`，默认视图切 `'all'`；沿用 §2.3 核实结论
- 相关 state/effect（signals 拉取过滤链）随之清理，不留死代码
- 回归：三个深链协议行为逐个实测不变

### 刀件 2：成交确认队列（进客户页，标「待确认」tab 或队列区）

- 数据源：疑似成交候选（规则 isDealSignal/parseBuySignal 命中 + AI judgment 中 deal 类），带客户原话证据锚点（message_key 可回查）
- **机制钉死（2026-08-27 评审）**：本队列是**事后复核**机制，不是前置门闸——既有 deal rule 命中自动写 stage=won 的链路保持不变（动它 = 实质修改 P0-2A 写者契约 + 中途改变观察期 won 指标口径，明确不做）。队列内两类候选分别处理：① deal rule 已自动落 won 的 →「确认成交」= 人工背书记录；② 仅 AI judgment 判 deal、未落库的 →「确认成交」走 manual 合法写路径补落 stage=won（写 last_stage_change_at）
- 动作只有两个：**确认成交**（背书或补落，如上）/**误判忽略**（走 manual 合法写路径纠正回正确 stage + 记录误判类型供规则校准）
- 队列条目带「生成跟进待办」按钮（复用现有手动待办进信号流机制）——队列在客户页是拉模式，补一个推出口避免名单吃灰；因价名单 30 人试点靠它验证「名单→行动→回流」闭环
- 同一队列承接因价流失名单（P0-5 §2.5，30 人试点）作为「疑似流失」类目
- 设计期必须先评估：能否扩展现有「信息待确认队列」（infoPendingQueue）支持新类型，而非新建第二套队列真源
- 护栏不变式：名单/AI 候选不得自动改 stage；确认前不占漏斗成交口径以外的任何统计

### 刀件 3：新建档客户进入信号流的分批节流

- 问题场景：P0-5 第三刀批量建档（source='p0-5-scan'，**规模以第三刀实际落库量为准**——第一刀实测自然好友高置信仅 2 / 灰区 21，批量主要来自真实留资线索入池后的先验人群），若全部立即产生今日行动卡，单日卡片洪水会淹没日常节奏
- 目标：新导入客户按分批（每日上限 N，N 待定）逐步释放进信号流，或按 lastContactAt 时间窗分层激活
- 具体机制设计时再定；约束：不修改 getUnifiedSignals 口径本体，节流发生在候选产出侧
- 与 P0-5 第三刀验收联动：getActionFunnel/周报剔除 source='p0-5-scan' 的断言在此一并落地

## 四、红线（沿承既有契约）

1. 不新建第二 stage 写路径——确认成交只走既有 legalStageWriters（manual/deal）
2. AI 判断 append-only、手动覆盖权利（P0-2C 语义）不被任何新队列破坏
3. 所有聊天证据读取统一走应用读取层（HTTP API / chatService），脚本不直连 WCDB
4. 新增 UI 不引入第二套行动卡组件——徽章深链复用现有导航
