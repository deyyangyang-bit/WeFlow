# 设计 · Hermes MVP（Phase 2 第一批：W8-W9）

> 状态：设计定稿（2026-09-06 增补刀 5「问数据」，用户确认业务数据联动为刚需），待用户确认后拆提示词给 GLM。
> 范围：PRD v3.4 §6 的 2.1（Hermes MVP 三件事）+ 2.2（权限链收口）+ 2.3/2.7（知识治理底座，问答的前提）+ 2.6（采用率埋点，与 Hermes 同天上，铁律不许后补）+ 问数据（业务库联动，见刀 5）。
> 不在本批：2.4 AI 首次分类（商机判定部分卡评测标注）、2.5 档案持续更新、2.9 效果回流、2.10 评测（基建已备）、2.11 微信推送、Phase 3b WeKnora。

## 0. 一句话

销售在聊天里问「这车续航多少」→ Hermes 从知识库（只读已发布条目）查出答案、注明引用自哪条 → 知识库没有就生成一条「知识提案」进审核队列 → 主管批准后发布；问「今天我该先跟谁」→ 直接查业务库，把真实数据说成人话。**AI 永远不自己发布**（宪法铁律）、**数字永远来自查询结果不是模型编的**，每一次「提案→人处理」都被埋点记录。

## 2. 刀序（四刀，每刀独立可验收）

### 刀 1 · 知识治理底座（2.3 + 2.7 前置）

1. **宪法 §3 先行登记**，再动 schema：`knowledge_base` 幂等 ALTER 加 6 列——`status`（staging/published/rejected，默认 staging）/ `authority`（official/community）/ `version`（INT 默认 1）/ `ttl_date`（到期日，可空）/ `reviewed_by`、`reviewed_at` / `reject_reason`。
2. KnowledgeBasePage 加「待审核」区：staging 条目列表，逐条「发布 / 拒绝（必填拒因）」；published 条目带 authority 徽标；rejected 沉底留档（拒因反哺，不删）。
3. 存量迁移：库里 219 条（产品 158 / 话术 59 / FAQ 2）一次性置 `status=staging, authority=community`——**治理版上线后它们默认不可被问答引用**，主管逐批审核发布。价格类条目标注「与产品库对账，冲突以产品库为准」（提示文案，本期不做自动对账）。
4. 本机知识库不删任何东西（PRD：迁移前照常使用 + 中央主机离线兜底）。

### 刀 2 · 采用率埋点（2.6，与 Hermes 同天上 = 与刀 1 同 commit 或紧随其后）

1. **宪法 §3 登记**新表 `proposal_event`：`event_type`（proposal/knowledge/action 三类）/ `stage`（generated/viewed/accepted/modified/rejected/expired）/ `entity_type` + `entity_id`（指向提案对象）/ `actor` / `created_at`；append-only，通用五列。
2. 三个写点先挂上（后续提案类功能天然继承）：
   - 信息待确认：applyInfo accept/reject → 写 proposal/accepted|rejected；
   - 知识审核：发布/拒绝 → 写 knowledge/accepted|rejected；
   - 行动卡完成：completeSignal → 写 action/accepted（generated/viewed 由既有任务创建/卡流渲染点补）。
3. 只读聚合：复盘页或设置加一行「近 7 天提案采纳率 X%（采纳+改后采纳）/ 处理 N 条」——PRD DoD 只看这两个数，不做花哨漏斗图。

### 刀 3 · 带引用知识问答（2.1 第一件）

1. 入口：聊天页会话侧栏 + 客户档案「AI 工具」下拉里加「问知识库」。
2. 检索：**关键词 LIKE 匹配起步**（title/content/tags），只查 `status='published'`；向量检索是 Phase 3b（WeKnora），本期不做。无命中 → 「知识库里没有答案」+「生成知识提案」按钮。
3. 组答案：命中条目（脱敏后）+ 问题 → callChatCompletion（temperature 0.2）→ 回答末尾固定格式列出引用条目（`引用自：《title》（v3）`），点击跳知识库对应条目。
4. 铁律：LLM 只读 published 条目；答案展示固定带「知识库答案，仅供参考」标识；**不自动发送给客户**（裁决 6：AI 碰不到发送键）。
5. 问答事实落埋点：generated（出答案）/ viewed（展开）——复用刀 2 的表。

### 刀 4 · 知识提案 + 确认队列升级（2.1 第二、三件 + 2.8 部分）

1. 知识提案写入路：问答无命中生成 / 手动「补充知识」→ 写 `knowledge_base` staging 行（source=proposal）+ 埋点。审核走路径 = 刀 1 的待审核区。
2. 确认队列 UX 升级（2.8 挑两个收益最大的）：信息待确认 + 知识审核两区都支持「批量通过」（勾选多条一次确认，防确认疲劳 PRD 点名）；知识审核区加「只看 diff」（提案与现有条目冲突时并排显示差异）。
3. 证据规范沿用：提案带 evidence_key（客户原话锚点）才允许进队列（宪法 §1.10）。

### 刀 5 · 问数据（业务库联动，2026-09-06 用户确认为刚需）

1. **入口与刀 3 合一**：同一个「问一问」输入框，先做意图分类——知识类（产品参数/话术 → 刀 3 知识检索）vs 数据类（业务问题 → 本刀）。分类用规则关键词起步（「今天/我的/多少/哪几个/到哪了」等指向数据类），拿不准按知识类处理（答错知识比查错数据代价小）。
2. **数据类走结构化查询，不走模型幻觉**：内置一组固定查询模板（每个模板 = 一条参数化只读 SQL + 文案模板）：
   - 「今天要办什么」→ 今日行动卡 + 晨间摘要（复用既有服务读口）
   - 「我的商机/快凉的商机」→ opportunity 按阶段 + 沉默天数排序
   - 「某客户到哪步了」→ 商机阶段 + 最新合同 + 最近信号时间
   - 「这个月到款多少」→ statsOverview 口径（与合同页数字同源）
   - 覆盖不了的问题 → 「这个问题我还不会查，知识库里也没有」+ 生成知识/能力提案入口
3. **铁律（进测试静态断言）**：回答里的每个数字必须来自查询结果行；LLM 只做两件事——意图分类兜底与把结果行转成人话；prompt 里只传查询结果（脱敏后），**不传原始聊天**。
4. **权限继承**：销售身份提问时所有模板查询先过 `filterByOwner`（§2.74），查不到别人名下的数据；越权测试进 DoD（销售问「李林辉的商机」→ 只返回本人数据或提示无权）。
5. 埋点复用刀 2：问数据 generated/viewed 照记。

## 3. 权限链（2.2 收口，不建大 RBAC）

本阶段权限链 = 宪法已有三样的形式化，不引入新框架：

1. **AI 三档**（A/B/C）继续是总闸门；
2. **Tool 白名单注册表**（一个常量清单 + 注释）：Hermes 本批可调用的工具 = 只读查询（knowledge 检索 / customer 档案读 / assignment 读 / 刀 5 问数据模板四个）+ B 类提案写点（知识提案 / 信息待确认）；C 类（改归属/合并/发布/对外发送）**不在清单里**，调到即拒。
3. 越权测试进 DoD：销售查不到他人客户（owner 过滤已有）+ Hermes 工具白名单外调用返回 E403。

## 4. 明确不做（防 scope 蔓延）

- 向量检索 / WeKnora / RAG 底座 → Phase 3b
- AI 自动判商机、AI 首次分类的商机部分 → 卡评测标注（≥100 条）
- 微信推送（2.11）→ W11，通道选型后单评
- 双向 bot → PRD 已封杀（封号风险）
- 价格自动对账 → 本期文案提示，人工对账

## 5. 验收（对应 DoD）

- 每刀：tsc 双门槛 / 新测试套件（知识治理状态机 / 埋点写点幂等 / 问答只读 published 静态断言 / 白名单外调用拒绝）/ 产物重建 / HANDOVER 增量 / 单 commit 不 push。
- 整批 DoD：销售在聊天页问一个真实产品问题 → 得到带引用的答案；问「今天我该先跟谁」→ 得到的名单与今日行动页完全一致（同源查询）；知识库无答案 → 提案进审核 → 主管发布 → 再问能答；复盘页能读到采纳率数字；销售问他人名下数据 → 查不到。
