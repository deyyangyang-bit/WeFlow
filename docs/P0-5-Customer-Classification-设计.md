## 二、分类模型：四层漏斗

```
全部联系人（~2,837）
      ↓ ① 身份过滤（0 元）
有会话数据的联系人
      ↓ ② 来源先验分流（新增，0 元）——按三级匹配关联（见 §2.2a 末条）
   ┌──────────┴──────────┐
留资线索 + 已建档客户          自然加的好友
（lead 表 ~872+ / profile 218）（无先验身份）
   │                          │
按当前阶段分组                规则证据评分（§2.2）
评估卡点与流失原因            ↓ ③ 分数区间确定性分流
   │                     高置信 ──→ 进建档刀
   │                     灰区 ────→ AI 精判
   │                     待观察 ──→ 不处理
   └────────────┬────────────┘
                ↓ ④ 附加产出：因价流失名单（§2.5，两条路径都算）
```

**来源先验双路径原则（§2.2a）**：
- **留资线索 / 已建档客户 = 天生潜在客户，不需要聊天关键词证明采购意向**。评分只用于判断其当前阶段（是否已联系/已报价/流失），不用于「是不是客户」的准入判定；
- **「待观察」对先验人群不适用**——时间衰减不得把留资客户沉底。一年没聊的留资线索不是"待观察"，而是「未成交存量」（复访名单），这恰恰是价格异议因素下最值钱的一批人；
- **先验人群的阶段分组走纯规则分桶**（¥0，与 §2.5 因价名单共用同一次扫描产出的证据，不送 AI）：有报价信号 →「已报价」；有成交词 →「已成交」；价格异议 + 超 90d 无互动 →「疑似流失（因价）」；无任何信号 →「未联系存量」。已建档 218 人直接读现有 canonical stage，不另算；
- **lead ↔ 微信好友关联走三级匹配**（按代码事实，优先级从高到低）：
  1. **`lead.account_id` 硬链接**——转客户的线索在转化时已写 account_id 并置 status=ACCOUNT（crmLeadService.ts 转化事务），直连会话零歧义；
  2. **`lead.wechat` 字段精确匹配**——现行生产表列名即 `wechat`（⚠️ `contact_wechat` 仅是旧壳表迁移兼容代码 crmDbService.ts:374 里的回退读取，不是现行 schema 列名）；
  3. **alias_map 别名模糊匹配**——兜底；
- 三级都关联不上的留资线索保持独立名单输出（不强凑关联、不伪造）。

### 2.1 第一层：身份过滤

排除：无名 session（**2026-08-27 校准后收紧**：只要无展示名一律剔除，不限 wxid 形态）、
备注前缀「删除我的人」（对方已单删用户，2026-08-27 用户确认剔除，现存 101 人）、
内部/测试账号、群机器人/系统账号、工具号（@weclaw 等机器人域名、filehelper 文件传输助手、weixin 团队助手等）。

> ⚠️ **业务红线（2026-08-27 用户拍板）：严禁按行业词过滤联系人**——物流公司（韵达/百世等快运）、
> 同行厂商（龙工等）、人事 HR 在本业务里**大部分是真实客户**（叉车买卖租赁的买家方），
> 「看起来像同行」不构成非客户证据；他们的准入只由聊天证据评分决定。

供应商、同行、物流联系人同样**不在第一层杀掉**——交给评分自然沉底，避免误伤潜在转介绍人。

### 2.2 第二层：多级证据评分（Customer Candidate Score）——仅适用于「自然好友」路径

**关键升级点：不叫「规则命中=潜在客户」，改为按会话累计打分。** 留资/已建档人群不走本层准入（见 §2.2a），只借同一套正则组件做阶段与归因判断（§2.5）。

分值表初版（v0，全部由现有正则组件推导，真实分值以第一刀抽验后校准为准）：

| 证据 | 分值 | 来源组件 |
|---|---|---|
| 采购意向表达 | +30 | `BUY_INTENT_RE` |
| 明确数量 | +30 | `parseBuySignal().quantity > 0` |
| 明确型号/吨位 | +35 | `BUY_DEVICE_RE` / `BUY_TON_RE` |
| 成交语义（弱化处理） | +40 | `isDealSignal` 且未被 DEAL_EXCLUDE 排除 |
| 报价后继续互动（暂缓 v0） | — | 需消息序列上下文，第一版不做 |
| 转述模式（我朋友问/帮我问） | −25 | 关键词组 |
| 时间衰减系数 | ×1.0/×0.8/×0.5/×0.2 | 最近消息 ≤7d / ≤30d / ≤90d / 更久 |

- **按会话累计**（同一人多条证据相加），非单句命中；
- 单条消息内多个命中**只取该消息最高分一项**，不累加（如一条消息同时命中型号+数量，只计 +35）；跨消息才累加，防止单句刷分；
  - ⚠️ **量化后果（已认知，待第一刀数据校准）**：单条消息理论上限为成交项 +40，故任何「一句话问清楚的爽快客户」（如"我要3台3吨电叉，多少钱"=+35）都够不到 70 分高置信线，会全部落灰区送 AI——高置信段实际由**跨消息多次互动**触达（多次追问才是真客户，语义自洽但更保守），灰区量级将大于 §五 的 200~400 估计，AI 成本可能翻倍。备选方案：放宽为「单条最高一项 + 第二高项半价」（上例 = 35+15 = 50）。⚠️ 注意半价方案的数学上限：单条最高组合 = 成交 40 + 型号半价 17.5 = 57.5，**仍 < 70**——它改变的是多消息累加速度，救不了单句爽快客户；若第一刀数据后真要让强信号单句直达高置信，真正的杠杆是**降 70 阈值**或**单条消息允许组合封顶**（如单条上限 60），复盘时别在半价方向上讨论。**v0 先按现语义执行**，第一刀真实分布出来后再定；

- **时间衰减按每条证据各自的消息时间计算**（非按会话最近消息统一折算），逐条打折后再求和；
- **成交证据单独放缓衰减**（≤90d ×1.0 / ≤365d ×0.8 / 更久 ×0.5，不设 ×0.2 档）——一两年前成交后沉默的老客户恰恰是「值得销售花时间」的人，不应被 ×0.2 沉底；
- 负分项 v0 只有「转述 −25」一条，**同行/供应商/广告类负向规则不在 v0 预先加**，靠第二刀抽验暴露误判类型后再补（第一刀报告须预留误判类型统计维度）；
- 分数是**派生读模型**，不落任何新表、不开新真源。

### 2.3 第三层：区间分流

| 区间 | 判定 | 动作 |
|---|---|---|
| Score ≥ 70 | 高置信潜客 | 进第三刀直接建档 |
| 30 ≤ Score < 70 | 灰区 | 送 `classifyStage` AI 精判 |
| Score < 30 | **待观察** | 不处理。没有证据 ≠ 不是客户，沉默客户保留活性 |

阈值 70/30 为 v0 拍脑袋值，以抽验集 Precision/Recall 曲线校准。

### 2.4 第四层：AI 只吃灰区

预算沿用 classifyStage 既有约束（≤500+100 token）。结果经 `persistClassification` 既有路径落库——**stage 六值真源不被破坏**；`extractEvidence` 锚点保证每条 AI 判断可回查原话。

**AI 输出 → 动作映射（钉死，避免第三刀临时决策）**：

| classifyStage 输出 | 动作 |
|---|---|
| new / contacted / quoted / negotiating / won | 视为客户，进第三刀建档 |
| dormant | 视为客户，建档且保留 activityState=dormant（合法输出值，不得掉到表外） |
| lost | 建档但标流失，不占销售精力 |
| unknown（合成位，见下） | **不建档**，退回「待观察」——AI 无法确认是客户 ≠ 不是客户 |

即灰区的判决问题不是「stage 是什么」而是「是否客户」：前五值+lost+dormant = 是客户，unknown = 证据不足，维持待观察活性。（注：本层只作用于自然好友路径；留资/已建档人群不经灰区直接入客户池分组。）

**unknown 的产生机制（代码事实钉死）**：classifyStage 的合法输出里**没有 unknown 值**（`CustomerStage` 仅七值）；而现行 prompt 规则 2「消息太少无法判断→输出 contacted」恰好会把灰区中证据不足的会话兜进「视为客户建档」。故扫描模式采用**置信度门槛**：`confidence < 0.6` 或分类失败（返回 null）一律按 unknown 处理。不改生产 prompt——现有链路行为零变化，门槛只存在于 P0-5 扫描路径。
（注：`parseClassification` 对 AI 未返回 confidence 的情况默认填 0.5，同样落入门槛下方按 unknown 处理——**这是有意为之的保守方向**：AI 偷懒不给置信度 = 证据不足。第一刀若见 unknown 比例偏高，属预期行为而非链路故障。另：prompt 明示 dormant「由系统判定，AI 一般不输出此值」，映射表中 dormant 行是防御性兜底，非现实分支。）

### 2.5 附加产出：因价流失名单（两条路径都算，商业价值优先级最高的单张表）

**动机**（用户拍板业务事实）：非成交主因常为价格异议——「问过价之后没下文」「说过别家便宜」的人不是垃圾数据，是**降价活动/老库存特价就能捞回的复访名单**。

**实现方式**：复用 `parseRiskSignal` 的 `RISK_PRICE_RE`（太贵/底价/还能不能便宜）与 `RISK_COMPETITOR_RE`（别家便宜），在第一刀扫描消息时顺带现算。**不依赖 crm_risk 表落库**（该表现状 0 行，识别器从未在生产链路被触发过）——名单由扫描直接产出报告，是否落库属第三刀拍板项。

| 名单字段 | 来源 |
|---|---|
| 客户 + 最近价格异议原话 | 扫描命中 RISK_PRICE_RE / RISK_COMPETITOR_RE 的客户消息（带 message_key 可回查） |
| 当前状态 | 已建档 → canonical stage；未建档 → 先验人群规则分桶（§2.2a）/ 自然好友分数段 |
| 建议动作档位 | 报价后沉默 / 比价后转向 / 仅问价未报价 |

**红线不变式**：名单只是报告产出，不自动改任何客户的 stage——「价格异议」≠「流失」，stage 归类仍走既有写路径资格规则。

## 三、分刀计划（刀式节奏）

### 第一刀：全量评分扫描（只读，零写库零 AI 零 UI 改动）

1. app 内一次性任务（dev 设置页触发或启动参数），照搬 backfillEnrich 的串行+防抖模式
2. `getSessions()` 枚举全部会话 → 对每个会话**近 365 天**的消息跑评分（时间衰减使更旧消息权重 ≤0.5，限定窗口同时控制全量扫描耗时）
3. **唯一产物 = 一份报告文件**（+ Excel 验证清单，用户拍板）：
   - **双路径人数分布**：来源先验分流结果——留资线索关联匹配多少（三级匹配各自命中率：account_id 直连 / wechat 精确 / alias_map 别名）/ 已建档 218 / 自然好友进入评分的基数
   - 自然好友三段分布（高置信 / 灰区 / 待观察）+ 先验人群阶段分组
   - 每段 Top 样本（联系方式脱敏 + 分值明细 + 命中 message_key 可回查）
   - **因价流失名单 v0**（§2.5）：价格异议/比价信号命中样本 + 当前状态归组——两条路径都会出现在这份名单里
   - 「2837 中实际有消息可算分的真实数量」——补上 §1.1 的空白，**按时间窗口分桶输出**（近 7d/30d/90d/365d 各有消息的会话数）
   - 预留「误判类型」统计维度占位（同行冒充 / 转述 / 老黄历成交 / 其他），供第二刀直接填
4. **分层抽样 100 人**出人工验证清单：高置信 60 + 灰区 25 + 待观察 15——只抽高分段只能测 Precision，待观察段的 15 个样本是回答「30 分阈值漏不漏人」（Recall）的唯一证据

**验收标准**：报告可复跑两次结果一致；样本抽查中每条分值能指回具体一条原话；**lead↔微信好友匹配率是核心产出指标**——若匹配率低，说明漏损在「加微」环节而非「聊天分类」环节，将直接改变 P0-5 的方向判断。

### 第二刀：抽验校准（纯人工 + 微调，无代码风险）

- 用户人工过验证清单，记录误判类型（同行冒充 / 转述 / 老黄历成交 / 其他）
- 校准分值表和阈值；若规则层 Precision < 85%，先改规则再花 AI 钱；若 ≥85%，进入第三刀
- **这一步的成本是用户一小时，收益是后面每一块钱都花在刀刃上**

### 第三刀：建档落库（等第二刀绿灯后才开工）

- 高置信段：走现有增量建档链路落 customer_profile
- 灰区段：批量串行调 `classifyStage`（隔日晚间低峰执行亦可），经 persistClassification 落库
- **批量写一律打 `source='p0-5-scan'` 溯源标记**——一次性给 200~400 人写 stage 会在漏斗「近 7 天新增进漏斗客户数」和周报热/冷基线上造成非业务尖峰，违反观察期「分不清指标变化是业务自然变化还是中途改系统造成的」铁则；走既有写路径不变，但窗口统计必须能识别并剔除这批回填
  - **验收标准（标记只在消费者真正剔除时才有意义）**：getActionFunnel 新增进漏斗口径、销售周报热/冷基线两处消费者必须显式过滤 `source='p0-5-scan'`，第三刀收口验收须包含「剔除后窗口统计与回填前一致」的断言；打了标记没人读等于没打
- 估算成本：灰区 200~400 人 × ≤600 token ≈ **¥0.5~1**（对价方案二的 ≈¥3 再省一半以上，因为大部分候选根本不用送 AI）

## 四、护栏契约（红线）

1. **分数只是派生读模型**——不建评分表、不开第二 stage 真源；任何落库行为都走既有 classifier 写路径（P0-2A 六刀契约不破）
2. **每条判断带 message_key 证据锚点**——不可回查的判断视为不存在（P0-1/P0-2C 同款诚实原则）
3. **读取统一走 chatService/wcdbService 应用读取层**——脚本不得绕过解密层直读 WCDB
4. **无名 session 永远不出现在任何一层输出里**（E3.2 门控语义延续）
5. **不做 S/A/B/C/D 分层、不做经营中心 UI**——那是数据底座可信之后的事，本设计明确不做
6. **AI 判断 append-only 不覆盖手动档案**（P0-2C 去重窗口语义沿用）
